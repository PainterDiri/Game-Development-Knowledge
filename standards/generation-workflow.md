# 课程生成流程

## 0. 先读规范并锁定范围

读取 `AGENTS.md`、`roadmap/README.md`、`roadmap/course-index.json` 和相关 standards。按 `order` 找到下一门 `scaffolded/planned` 课程；除非用户明确要求，不同时生成多门。若本次是重做已发布课程，先把状态改为 `in-progress`，完成后再决定是否恢复 `completed`。

## 1. 研究与前置检查

- 根据课程索引确认深度、前置出口和课程角色；
- 做一个可执行的零基础诊断或补桥；
- 检索官方文档、标准、论文、源码、大学教材；
- 对版本敏感内容记录版本、访问日期、用途、限制和冲突；
- 研究资料只服务写作，不生成公开的“参考书目/研究笔记”页。

## 2. 先设计课程地图

在写任何正文前，先画：

```text
前置能力 → 真实问题 → 概念依赖 → 章节产出 → 章节练习 → 课程主实践
```

README 逐章列出前置输入、要解决的问题、核心产出、完成证据、下一章用途，并标记必修/选读。按课程特性决定章节结构：C 课程应围绕值、对象、内存、生命周期、模块、错误和验证递进；Git 课程应围绕状态转移、共享历史、构建证据和恢复递进；Unity 课程才围绕生命周期、玩法组件和编辑器工作流。

课程地图完成后再建立 `lessons/`，不要批量创建占位页。

## 3. 逐章生成详细正文

每章从可观察问题开始，按“普通语言 → 正式模型 → 最小例子 → 逐行解释 → 故意失败 → 边界/取舍 → 验证 → 游戏映射 → 下一章”展开。复杂知识拆成多章，不用一段结论替代推导。第一次出现的命令要说明：它读取/修改什么、不会修改什么、如何验证、误用如何恢复。

每章末尾必须放代表性练习，题面后直接放折叠提示和完整讲解；不能再创建集中式练习题页面。

## 4. 设计唯一主实践

主实践必须和课程知识直接相关，并给出可运行的最小版本、指导代码、里程碑、故意失败和验收。实践可以使用 Unity，但不要求它成为最终肉鸽主项目的接缝。课程元数据只描述本课程实践项目；推进完整 RogueSlice 由专门课程负责。

实践的工作目录必须是仓库外或 `.practice/<course-slug>/`。公开 `code/` 只读，实践页必须给出：

```bash
python3 scripts/init_practice.py --course <slug>
git check-ignore -v .practice/<slug>
git status --short --untracked-files=all
```

并解释预期结果、清理风险和 `git clean -fdx` 禁忌。若学习者要在实践内部练习 Git，应在该目录单独初始化仓库并验证根目录。

## 5. 生成后求知者验收与返工

生成不是写完文件就结束。必须先以好学但不熟悉本课的读者顺序通读：执行关键命令、尝试章节练习、检查术语和代码；再以专业审查者检查机制、边界、复杂度、失败、引用和游戏用途。重点找：讲不透、跳步、跑题、重复、错误前提、缺少验证、缺少反例、可进一步展开却被一句带过的知识。

每章验收至少记录：

- 本章第一个问题是否不依赖未解释术语；
- 每个命令读取/修改什么、不会修改什么、成功/失败如何观察；
- 每段代码的输入、输出、状态变化、前置条件、生命周期和可运行性质；
- 一个实际执行的成功例子、一个实际触发的失败例子及修复后的回归；
- 章末题是否能在不翻到下一章的情况下作答，解析是否讲推理而非只给答案；
- 这一章是否真的为下一章产出可消费的概念或代码。

发现问题后直接修改 README、章节、练习、实践或代码，再重复审查。至少要对 D3 核心难点做一次“从故意失败到修复”的闭环验证；只把问题写进研究笔记或审查报告而不返工，视为未完成。

## 6. 发布门禁

依次运行：

```bash
python3 scripts/sync_docs.py
python3 scripts/check_repo.py
git diff --check
mkdocs build --strict
```

若有 `practice-bundle.json`，测试 ZIP 能在新目录解压、代码能运行，且没有缓存、秘密、个人路径或答案。最后人工检查正确性、可复现性、游戏相关性、版权、隐私和实践隔离，再更新课程索引状态。未经用户明确授权，不 push。
