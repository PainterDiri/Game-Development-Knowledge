# 实践设计标准

## 先判断是否值得做

实践必须同时具备较高信息增益和明确验收，并至少满足“可复用、可缩放、能暴露典型失败”中的一项。否则将验证合并到正文，不单独创建练习。

## 数量与时长

- 每门课最多 **1 个主实践 + 2 个微实验**，不是必须凑满；
- 微实验通常 15–45 分钟，只验证一个机制；
- 主实践通常 2–6 小时，连接多个知识点；
- 超过 6 小时的内容应挂接 P0–P5 主项目并拆成可验收切片。

## 题面必须说明

1. 要验证的机制，而不是笼统作品名；
2. 输入、输出、约束、允许修改的范围；
3. 完成证据：测试、日志、截图、性能数据或可观察行为；
4. 至少一个故意失败案例；
5. 时间不足时的最小版本；
6. 环境、版本、运行命令和清理方式。

## 解法必须帮助自学

`labs/solutions.md` 按需提供：

- 最小提示；
- 推荐拆解顺序与关键不变量；
- 参考实现、伪代码或代码入口；
- 验收命令、预期结果与失败诊断；
- 替代方案和适用约束；
- 向肉鸽、Unity、UE、服务器或工具链的迁移。

参考方案不是唯一答案。评价重点是约束是否满足、失败是否可诊断、结果是否可复现。

## 选择实践载体

| 知识类型 | 优先载体 | 原因 |
|---|---|---|
| 算法、数学、随机 | 小程序、测试、图表或交互模拟器 | 快速复现和比较数据 |
| 内存、并发、系统 | C/C++ 最小程序、基准、调试器 | 能直接观察底层行为 |
| 网络、数据库、服务 | 本地多进程/容器化最小服务 | 明确信任边界和故障路径 |
| 玩法、工具、内容管线 | Unity | 快速形成可玩反馈与编辑器工具 |
| 大型框架迁移 | UE C++ + 蓝图 | 对照模块化、反射、复制和团队边界 |

不要为了“像游戏”而强行引入引擎，也不要为了“底层”而拒绝使用能提高验证效率的工具。

## 默认单页入口

为了降低操作成本，新课程优先使用 `practice.md`：把目标、环境、任务、代码入口、里程碑、折叠提示、参考路线、验收、故意失败、常见失败和替代方案放在同一页。只有实践内容足够大、需要多人协作或有独立代码仓库时，才拆成 `labs/`；拆分后也要从课程首页提供一个明确入口，不让学习者在多个页面之间猜测顺序。

## 主项目整合：先验证，再接入

课程实践是否与小以撒主项目结合，不能只按“看起来像游戏”判断。生成课程时先读取 `roadmap/course-index.json` 中的 `practiceTrack`、`integrationMode` 和 `projectSlice`：

- `supporting-lab/export`：C、数学、算法、组成和操作系统等课程先用小程序、库、fixture、基准或推导验证；只导出经过测试的接口或数据，不把 Unity 当作底层实验的替代品；
- `shared-unity/direct`：软件工程、AI、引擎和 Unity 生产等课程可直接在学习者的唯一 Unity 项目中完成一个小功能，但必须限制修改目录、写明状态拥有者，并保留独立测试；
- `adapter`：通过薄适配器或稳定契约接入，课程内部实现不得渗透到 UI、场景或平台代码；
- `online-sidecar/standalone`：网络与 UE 课程保留旁路服务或独立引擎项目，主线可以选择性消费结果，不得让多人服务或第二引擎阻塞单机纵切片。

每个主实践都要写一段“主项目接缝”，至少说明：输入/输出、所有者、允许修改的目录、回滚方式、固定 seed 或故障样本、主项目冒烟验收。接入失败时，学习者应能退回实践的独立最小版本继续学习。

## 可下载实践代码

课程网页负责完整教学：正文、实践题面、提示、答案、验收和失败诊断都应能直接在线阅读。只有经过审查的代码、测试、fixture、配置和主项目接缝才进入下载包；不要把网页正文和折叠答案默认复制进 ZIP。

有公开实践代码的课程使用课程目录下的 `practice-bundle.json` 下载清单。schema 2 必须声明 `downloadType: "practice-code"`，并用显式角色列出 `starter-code`、`reference-code`、`test-fixture`、`integration-contract` 等输入。禁止打入构建缓存、个人状态、密钥、日志、绝对路径或平台发布产物。起始代码与参考实现能拆分时必须分别标记；当前只有参考基线时要明确标记为 `reference-code`，不能伪装成隐藏答案。

没有独立代码价值的课程可以下载数据、fixture、图表脚本或参考输入，但不能为了凑下载包强行引入 Unity。
