# 实践设计标准

## 每门课只保留一个主实践

课程实践用来把本课程的核心机制组合成一个可运行、可诊断、与游戏开发直接相关的小项目。它不再承担“与最终肉鸽主项目逐课接缝”的职责；推进完整主项目由专门的 Unity 生产课和毕业项目课负责。

主实践通常为 2–8 小时，可分里程碑完成。正文中的短验证和章末练习不算第二个实践。不要再额外创建两个微实验来凑配额；确有价值的 10–30 分钟实验直接放入相关章节。

## 题面必须说明

1. 要验证的课程机制与游戏用途；
2. 输入、输出、约束、允许修改的范围；
3. 环境、语言/引擎版本、构建与运行命令；
4. 最小可交付版本和逐步扩展路线；
5. 关键代码的作用、调用顺序和状态变化；
6. 完成证据：测试、日志、截图、性能数据或可观察行为；
7. 至少一个故意失败案例、诊断路径和修复后的回归；
8. 清理方式、已知限制和可选拓展。

Unity 是玩法、内容工具和资源管线课程的优先载体；C、算法、系统、网络等课程可以使用更适合观察机制的命令行程序、测试、模拟器或本地服务。载体必须服务于课程，而不是为了统一而强行引擎化。

## 个人实践必须与仓库隔离

仓库内 `knowledge-sets/<slug>/code/` 是公开教材资产，不是个人工作目录。所有实践页必须把以下流程写清：

1. 在仓库根目录运行 `python3 scripts/init_practice.py --course <slug>`，把白名单中的起始/参考代码复制到 `.practice/<slug>/`；
2. 运行 `git check-ignore -v .practice/<slug>`，必须命中仓库的 `.gitignore`；
3. 运行 `git status --short --untracked-files=all`，个人实践文件不应出现；
4. 只在 `.practice/<slug>/` 中编辑。若要练习 Git，可在该目录内部另行 `git init`，并用 `git rev-parse --show-toplevel` 确认当前仓库；
5. 不使用 `git add -f .practice/...`，不把个人实践复制回 `knowledge-sets/`；
6. `.gitignore` 只保护未跟踪文件。若误改了已跟踪教材文件，先用 `git diff -- <path>` 保存/检查差异，再复制到 `.practice/`，确认备份后才考虑 `git restore`；
7. `git clean -fdx` 会删除被忽略的 `.practice/`，不要在主仓库根目录运行。重要个人代码应另有仓库外备份或自己的独立仓库。

实践页的验收必须包含一次隔离检查。仅写“目录已被忽略”不够，必须给出验证命令和预期结果。

## 可下载实践代码

有公开代码的课程使用 `practice-bundle.json` 显式列出 `starter-code`、`reference-code`、`test-fixture` 等角色。下载包不得包含构建缓存、个人状态、密钥、日志、绝对路径或发布产物。参考实现不是唯一答案，也不得暗示学习者直接在仓库源文件上修改。
