# 内容质量规范

## 目标

每门课程都要形成可迁移的理解与交付能力，而不是生成一份很长、很像模板的 Markdown。游戏案例用于让抽象知识可观察、可验证，不能牺牲学科本身的严谨性。

## 固定的是证据，不是章节标题

每个核心知识点都必须覆盖以下证据，但**不要求使用同一组标题或相同比例**：

1. **定义与边界**：它是什么，不是什么；
2. **机制与不变量**：状态如何变化，什么必须始终成立；
3. **取舍与失败**：方案何时有效，何时失效，代价是什么；
4. **游戏映射**：在运行时、工具、服务端或生产流程中解决什么问题；
5. **验证**：如何用推导、代码、测试、日志、性能数据或反例证明理解。

课程地图必须先判断这门课最适合哪种教学形态，再设计章节：

| 课程形态 | 合适的主线 | 不应强套的结构 |
|---|---|---|
| 数学/理论 | 问题 → 建模 → 推导/证明 → 反例 → 数值实验 | 每节都硬塞引擎 API |
| 数据结构/算法 | 约束 → 不变量 → 实现 → 复杂度 → 基准与失败 | 只讲定义和标准代码 |
| 系统/底层 | 可观察现象 → 硬件/OS 机制 → 测量 → 诊断 | 用架构口号代替数据 |
| 架构/软件工程 | 需求与变化轴 → 状态/依赖 → 方案比较 → 演进测试 | 把某一种模式写成唯一答案 |
| 引擎/工具 | 最小场景 → 生命周期/API 边界 → 调试 → 项目化迁移 | 罗列编辑器菜单和 API |
| 生产/发行 | 交付目标 → 风险 → 流程与自动化 → 验收/回滚 | 大段行业常识和清单 |

同一门课也可以混合多种形态。章节数量、页面长度、图表和代码比例都由问题复杂度决定。

## 页面设计

- 一个页面聚焦一个可验证问题；过大就拆，过小就合并。
- 开头直接给问题、现象、失败案例或约束，不写泛泛动机。
- 新术语首次出现时给中文、英文、缩写和一句边界清晰的解释。
- 代码按需要使用“最小片段 → 可运行实验 → 项目化版本”，不是每章都必须三级齐全。
- 复杂关系优先使用 Mermaid 状态图、时序图、数据流图或可再生成的可视化；简单关系用文字，不为了美观强行画图。
- 图示必须在正文中被解释，并提供文字结论，不能让颜色或动画成为唯一信息来源。
- API 只在解决具体问题时出现，并标注版本；不复制参数表。

## 游戏开发主线

优先选择能暴露课程本质的案例：

- 肉鸽：房间图、种子随机、掉落、道具组合、状态效果、存档与复现；
- 动作：输入缓冲、固定时间步、命中帧、无敌帧、击退、相机和反馈；
- 3A：资源管线、动画、流式加载、性能预算、工具和协作；
- MOBA/FPS：权威服务器、预测、插值、快照、命中验证与反作弊。

“专业团队做法”只能基于公开资料或清楚标注的工程推断，并说明教学实现省略了什么。

## 题目与答案

题目数量由知识密度决定，不再按每章固定配额。通常整门课保留 **8–16 道核心题 + 1 道综合题**；较短的 D1/D2 课程可以更少。每道题必须至少检验一种高价值能力：

- 解释反直觉现象；
- 推导或维护不变量；
- 定位 bug 并设计验证；
- 比较两个方案的约束和代价；
- 把原理迁移到实际游戏系统。

默认将题目、最小提示和完整解析放在课程目录下的单页 `assessments.md`，让学习者不必在问题页和答案页之间来回跳转；只有题量或协作规模确实需要时，才拆成 `assessments/questions.md` 与 `assessments/answers.md`。无论采用哪种布局，每个题目 ID 必须一一对应，并提供按需折叠的最小提示与完整解析。解析包含结论、推理、边界、常见错误、验证和游戏映射；删除只有态度表达、没有可判定标准的泛泛主观题，多解题按约束评价，不伪装成唯一答案。

## 实践

“最多 1 个主实践 + 2 个微实验”是上限，不是配额。没有独立实践价值时，可以把验证合并到正文或主项目；不得为了凑数创建重复练习。

参考解法重点解释拆解顺序、关键不变量、验收证据、常见失败和替代设计。Unity/UE 实践可以只提供关键组件与场景搭建，但必须足以复现结果。

## 深度

- **D3**：能推导机制、实现简化版、分析复杂度/内存/并发等成本，并处理失败案例；
- **D2**：能解释原理地图、正确使用工具/API、完成可复现实验并迁移到至少两个场景；
- **D1**：能说明概念边界、适用场景、与主线的关系以及何时需要继续深入。

## 删除规则

发现以下内容直接删或改成验证：重复动机、学习鸡汤、无比较的技术栈介绍、无运行结果的大段代码、无用途的链接清单、为了显得全面而列出的几十个工具，以及只换课程名的模板段落。

## 正文深度门槛（完成状态）

`completed` 不能由“文件存在”推断。课程正文至少要让学习者完成一条从现象到证据的路径：

```text
问题/失败现象 → 术语与边界 → 机制或推导 → 具体示例/代码 → 反例与取舍 → 验证 → 游戏迁移/延伸
```

每个章节不必机械使用这些标题，但如果页面只有目录、结论、命令清单或实践链接，应判定为未完成。仓库检查会对完成课程检查正文长度和质量信号；人工门禁还要抽查示例是否真的能运行、失败是否可重现、结论是否超出来源支持范围。

课程首页（`README.md`）同时承担课程地图，必须让学习者在一页内知道：先读顺序、前置诊断、主实践/练习入口、完成证据和版本边界。课程地图不是额外目录页。

研究笔记和书目用于维护者追溯，不得拿它们替代正文解释；术语表不是默认学习路径，术语应在首次出现处就地解释。
