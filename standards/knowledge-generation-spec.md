# 内容质量规范

## 目标：生成真正能学习、能运行、能验收的教材

本仓库不是术语目录，也不是把大学课名换成游戏名。默认学习者可能第一次遇到指针、提交图、矩阵或 Transformer；课程必须让他从一个可观察问题走到可解释的模型，再走到可运行验证和游戏决策。

## 一、先画课程地图，再逐章写作

`README.md` 是课程首页和唯一地图入口，必须写清：

- 起点、前置知识、10–30 分钟诊断题或补桥；
- 一个核心问题和最终可验证出口；
- 章节的概念依赖：上一章产物 → 本章问题 → 本章产出 → 下一章用途；
- 必修与选读边界；
- 本课程唯一主实践、最小版本、代码入口和安全复制路径；
- 课程自身的游戏映射。不要把“未来接入 RogueSlice”写成每门课的硬性目标。

地图完成后才创建正文文件。D3 课程按概念依赖拆出足够知识单元；C、数学、算法、系统和 AI 的核心难点不能压缩成流水账。

## 二、每个知识单元必须完成教学闭环

每章至少要让学习者看到以下多数证据，核心难点全部覆盖：

1. **问题场景**：先展示任务、输出异常、崩溃、错误命令或一个游戏需求；
2. **术语与边界**：普通话解释，再给正式定义、反例和暂不讨论的相邻概念；
3. **机制/不变量/推导**：状态怎样改变，为什么成立，哪些条件不能破坏；
4. **从小到大的例子**：最小片段 → 逐行解释 → 可运行版本 → 项目化例子；
5. **故意失败与取舍**：给出可复现失败、成本/复杂度/维护风险和适用边界；
6. **验证**：命令、测试、推导、测量、日志、调试器观察或预期输出；
7. **游戏映射**：运行时、工具、资源、网络或生产中的具体用途；
8. **下一章连接**：说明本章产物如何被下一章消费。

每章开头用一两句话承接前章留下的问题；结尾必须包含“本章练习”，再用一段话连接下一章。不能以抽象术语表开头，不能用“本章介绍了……”代替因果链。不要用只有“机制/验证/游戏映射”标题的空壳章节；每个标题下面都必须有能让读者执行或推演的内容。

## 三、独立出题人与章末练习

章末练习由独立的“出题人”角色负责，而不是正文作者写完后机械补题。出题人先重新阅读本章的学习产出、定义、机制、不变量、边界、失败、验证和下一章用途，再调查教材/课程中的相关题型，最后按本章内容设计题目。详细规则见[章末出题人规范](question-authoring.md)。

### 题量按知识密度变化

不使用“每章固定 2 题”或“每章最多 5 题”的模板。窄章节可只有 1 道能判定核心误解的题；普通章节通常 2–4 道；多个相互依赖机制的章节通常需要 4–8 道；线性代数、离散数学、算法、证明、统计和综合计算章节可以根据覆盖需要超过 8 道。数量不是质量指标：如果第二题和第一题只换了变量名，应删除；如果本章有多个独立学习产出，却只有一道宽泛题，应拆题或补题。

出题人应在适合本章的情况下覆盖至少两类能力：解释机制、预测结果、修复故意失败、计算/证明、设计/实现、迁移与取舍。窄到只有一个核心误解的章节可以只用一类题，但不能为了凑第二类而注水。题面必须有具体输入、约束、边界或判定标准，不能只要求“谈谈理解”或“写一个验证”。

### 题目、提示和解析的位置与要求

不创建 `assessments.md`、`assessments/` 或其他独立“练习题”页面。练习放在所依赖章节结尾；每题有全课程唯一 ID，题面后紧邻完整讲解。最小提示是可选的：只有确实能解除卡点、且不会泄露方法/结论时才保留。完整讲解必须包含推理过程、成立条件或边界、常见错误、验证/判定方法和具体游戏映射；纯数学或理论题可以说明其对变换、相机、瞄准、碰撞、概率、数据结构或性能决策的影响。

出题人必须删除或重写以下候选题：纯抄定义、只复述正文、与其他题重复、泛泛“写出一个验证”、偷偷依赖下一章、没有可判定标准、或游戏映射只能硬加一句口号。题目数量、题型和是否需要提示，都要在出题人审题后决定。

推荐结构：

```markdown
## 本章练习

### C09-Q1：题目名
题面……

<!-- 只有确实有帮助时才保留这一块 -->
<details><summary>最小提示</summary>
只给下一步思路。
</details>

<details><summary>讲解与验证</summary>
解释推理、边界、常见错误、验证和游戏用途。
</details>
```

没有必要提示时，直接省略“最小提示”，但完整讲解不可省略。题目 ID 必须全课程唯一，题目、提示和解析不能拆到集中练习页。

## 四、篇幅由难点决定

- 第一次出现的变量、文件、进程、状态、指针、分支、向量等必须慢讲；
- 核心难点要拆开，允许多个例子、反例和实验；
- 历史背景、API 清单和行业口号要短；
- D3 课程至少 12 个连续知识单元，且每个单元有真实正文，不得靠标题数量充数；
- 一页正文不是合格的“课程”，完成课程的学习者应能不打开实践页就理解核心机制并运行至少一个章节验证；章节长度不是质量指标，但短到只能列术语、命令或结论时必须返工。
- 对 D3 课程的每个核心章节，至少提供一个完整推演例子和一个可复现失败；若某章的难点是算法、内存、并发、数值或协议，还要补充边界和取舍，而不能只引用主实践。

## 五、初学者可读性与专业复查

生成完成后必须进行两轮人工式验收，并根据问题重新写作，而不是只打勾：

### 求知者审查（从零学习者角度）

逐章尝试回答：

- 我能否在不知道本章术语时理解开头的问题？
- 每个代码片段的输入、输出、状态变化和关键行是否解释？
- 是否出现了未经解释的命令、符号、类型、API 或前置结论？
- 正常教材会展开的重要内容，是否被一句话带过？本章提到的每个重要名词，是否都有足够的边界、例子或明确的“本章不展开”说明？
- 我能否按命令运行并知道“做对了会看到什么”？
- 失败后我是否知道先看哪里，而不是只得到“注意安全”？
- 合上答案后，题面是否足够清楚、提示是否真的必要且不过度泄露、题量是否让我练习了本章的关键产出而不是重复劳动？

### 专业深度审查

逐章检查：

- 结论背后是否有机制、不变量、复杂度、生命周期、数值/线程/信任边界或来源；
- 示例是否覆盖边界，故意失败是否真的能复现；
- 相近概念是否比较了效果、风险和适用条件；
- 游戏映射是否是具体工程决策而非装饰；
- 章节是否跑题、重复、跳跃，是否需要合并、拆分或补写；是否存在教材/课程通常会教但本章完全遗漏的重要内容，或本章提到却没有解释到位的内容；
- 章末题是否覆盖本章主要产出，是否有重复/注水题、不可判定题或应补而未补的计算、反例、失败修复或设计题；
- Git 命令是否逐条说明改变哪个状态（工作区、暂存区、本地引用、远端引用或提交历史）、共享历史风险、验证和恢复路径；
- 实践是否能在不污染主仓库的前提下完成。

审查发现“讲不透、跳脱、可拓展却没展开”的地方必须回写正文或章末练习；验收记录写入生成任务结果，不发布研究笔记页。至少保留一份内部验收清单，逐章标出已实际运行的命令、失败输入、预期结果和返工点；清单可在任务上下文或临时文件中，不能变成公开学习者档案。

## 六、生成后验收必须产生证据

“已生成”不等于“已验收”。完成课程前，生成者必须按学习顺序做一次求知者走查，再做一次专业走查，并把发现的问题直接改回源文件。最低操作如下：

1. 在仓库外或临时目录运行章节中声称可运行的命令；记录输入、输出、退出码和平台/工具版本；
2. 对每个核心代码片段判断它是“可独立编译”“依赖前文类型的片段”还是“伪代码”，在正文中明确标注，不能让读者盲目复制；
3. 至少执行一个故意失败，确认失败确实由正文所说的原因触发，再执行修复和回归验证；
4. 合上答案尝试章末练习，检查提示不会直接泄露结论，讲解是否说明推理、边界、错误、验证和游戏用途；
5. 检查章节之间的术语、变量、文件路径和命令是否连续，删除跑题、重复或没有消费方的内容；
6. 若发现“读者必须猜”“命令只是罗列”“重要 API 只出现一次”“某结论靠经验而非证据”，不得只在验收报告里写备注，必须回写正文、练习、实践或代码。

课程 README 只能在上述走查和返工完成后把状态恢复为 `completed`。自动门禁用于拦截结构错误，不能替代这两轮内容验收。

## 七、实践和个人文件隔离

每门课只有一个主实践。实践页必须包含独立最小版本、逐步指导、关键代码、验收、故意失败、清理方式以及：复制到 `.practice/<course-slug>/`、`git check-ignore`、`git status`、禁止 `git add -f` 和误改已跟踪源文件的恢复流程。不得要求把练习直接写回 `knowledge-sets/`。

## 八、来源、版本和版权

先查官方文档、标准、论文、源码和大学教材。版本敏感结论在正文就地注明适用版本和访问日期；公开案例与教学推断分开；不复制受版权保护的整章、商业源码或私有文档。独立研究笔记和参考书目不进入课程目录。
