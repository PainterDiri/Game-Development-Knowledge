# 知识集生成规范 v1

## 1. 目的

为 `knowledge-sets/<course-slug>/` 生成能够替代零散教程、接近专业本科课程并面向游戏开发的**公开课程内容**。目标是**真正形成可迁移的理解和交付能力**，不是生成很长的文字。

## 2. 必须回答的五类问题

每一个核心知识点必须尽量回答：

1. **定义**：它是什么，边界在哪里？
2. **机制**：它如何工作，关键数据结构/状态/不变量是什么？
3. **取舍**：为什么选它，什么情况下不用它？
4. **游戏映射**：在游戏运行时、工具、服务端或生产流程中解决什么问题？
5. **验证**：如何用代码、测试、日志、性能数据或反例证明自己理解了？

## 3. 每章的固定结构

```markdown
# 章节标题

## 本章要解决的问题
## 先修与出口能力
## 核心概念（定义 + 机制 + 不变量）
## 从最小例子推导
## 游戏开发映射
## 反例与常见误区
## 实现/调试实验
## 小结：必须能回答的问题
## 参考来源
```

章节不能以大段背景、目录或泛泛的“重要性”开头；开头直接提出问题或展示一个可观察现象。

## 4. 内容颗粒度

- 一个页面聚焦一个可验证主题；过大的主题拆页。
- 术语第一次出现给出中文名、英文名、缩写和一句定义。
- 代码按“最小可运行片段 → 完整实验 → 项目化版本”递进。
- 每段代码写明语言、工具链、运行命令和预期输出。
- 对复杂概念优先画数据流/状态图/时序图，再上代码。
- 不能只给 API 清单；API 说明必须嵌在问题、机制和实验中。

## 5. 游戏开发主线

每门课至少绑定一个真实游戏问题。优先案例：

- 肉鸽：房间图、种子随机、掉落、道具组合、状态效果、存档与复现；
- 动作：输入缓冲、固定时间步、命中帧、无敌帧、击退、相机和反馈；
- 3A：资源管线、动画状态、流式加载、LOD、性能预算、工具和团队协作；
- MOBA/FPS：权威服务器、客户端预测、插值、快照、命中验证、反作弊。

案例应解释“专业团队为什么这样拆”，同时明确哪些是教学简化，不假装还原商业项目的私有实现。

## 6. 防注水检查

以下内容不能占用正文篇幅，除非它改变了实现决策：

- 重复的学习动机和泛泛鼓励；
- 无比较的“技术栈介绍”；
- 复制官方文档的 API 参数表；
- 没有运行结果的代码大段；
- 与课程出口能力无关的行业新闻；
- 为了增加字数而列出几十个可选工具。

## 7. 题目、答案与解析

每门课程必须生成三个公开评估文件：

- `assessments/questions.md`：每章 2–4 道高信息量题，另加 1 道综合题；
- `assessments/answers.md`：与题目编号一一对应，包含最小提示、参考答案、推理过程、边界、常见错误和游戏迁移；
- `assessments/rubric.md`：正确性、深度、游戏迁移、验证证据四项评分标准。

答案使用 `<details>` 折叠块，便于学习者快速查看但不在作答前被迫看到。答案不是唯一实现时，要明确允许的不同方案和评分要点。题目使用稳定唯一 ID，并与答案、评分要点一一对应。

## 8. 实践参考解法

每门课的 `labs/solutions.md` 必须为每个实践提供折叠的最小提示、推荐拆解顺序、关键不变量、参考方案、验证方法、常见失败和替代设计。可运行参考实现放在 `code/` 时，解法页必须给出运行命令、预期结果和限制。

实践答案的重点是解释为什么这样拆、如何证明正确、何时应改用其他方案，而不是给一份可以无脑复制的最终工程。Unity/UE 大型实践允许只提供关键组件和场景/测试搭建说明，但必须足以复现验收结果。

## 9. 自动续学与个人隔离

课程源目录不能包含具体学习者的进度、作答、错误、决策或实践输出。网站通过浏览器 `localStorage` 自动保存最后阅读页面、章节和滚动位置；学习者无需维护文件。个人实践若放在仓库中，按需使用被忽略的 `.practice/`。课程知识集必须能被多人直接访问且互不影响。

## 10. 深度要求

D3 课程必须包含：手写简化版、复杂度/内存分析、至少一个失败案例、测试与调试记录、游戏系统设计取舍。

D2 课程必须包含：原理地图、官方 API/工具的正确用法、与至少两个游戏系统的映射、一个可复现实验。

D1 课程必须包含：概念边界、适用场景、与主线的关系、进一步学习入口；不要求堆叠大量实现。
