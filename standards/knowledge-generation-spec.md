# 内容质量规范

## 目标：让零基础学习者走完一条可解释的路

本仓库不是术语目录，也不是把大学课程标题换成游戏名。默认学习者可能只知道“文件、程序、游戏”这些词，第一次遇到指针、分支、矩阵或 Transformer 时，需要看到问题、最小模型、例子、练习和下一步之间的关系。

课程正文必须同时满足两件事：

1. **初学者能沿着正文从不会到会**：每个新概念都有前置铺垫，章节之间有明确依赖，上一章的产物会成为下一章的输入；
2. **进阶者能获得工程深度**：不只背 API 或结论，还能解释机制、成本、失败、验证证据以及在游戏项目中的边界。

## 一、每门课先画“学习依赖图”，再写章节

`README.md` 必须作为课程首页和课程地图，至少写清：

- 学习者开始前需要会什么；若不满足，提供一个 10–30 分钟的诊断题或补桥微实验；
- 课程最终要解决的一个核心问题；
- 从第一个可观察现象到最终出口的章节顺序；
- 每章的输入、产出、依赖和完成证据；
- 哪些内容是必须掌握，哪些是选读拓展；
- 课程如何独立验证，以及如何通过 `practiceTrack`/`integrationMode` 接入 `RogueSlice`。

章节顺序优先遵守以下递进：

```text
现象/任务 → 最小术语 → 心智模型 → 单步示例 → 可运行实验
→ 多个例子与边界 → 工程取舍 → 游戏映射 → 综合实践
```

不得在学习者尚未知道“程序如何运行、状态是什么、输入和输出是什么”时，直接从“系统边界、架构分层、构建管线”或其他抽象总论开始。抽象模型应在一个具体失败例子之后出现，并回到具体例子验证。

## 二、正文结构由课程问题决定，但教学证据不能省

每个核心知识块至少需要覆盖下列证据；可以使用自然的小节标题，不要求每页套同一模板。生成前先把每个知识块登记到课程地图，避免“有标题但没有教学证据”：

1. **问题场景**：学习者为什么会遇到它，先展示一个可以观察的任务或失败；
2. **术语与边界**：中文、英文、缩写、反例和本节暂不讨论的相邻概念；
3. **机制/不变量/推导**：状态如何改变，为什么成立，哪些条件不能破坏；
4. **从小到大的例子**：先有最小片段，再有可运行版本，必要时再给项目化版本；
5. **失败与取舍**：至少一个故意失败、反例、复杂度/性能/维护成本或安全边界；
6. **验证**：命令、测试、推导、测量、日志或预期观察，读者能判断自己是否做对；
7. **游戏映射**：说明它在运行时、工具、资源、网络或生产中解决什么问题；
8. **下一步连接**：明确本节如何被下一节使用，不用“本章介绍了……”代替逻辑连接。

### 章节之间的因果链与篇幅

- 每章开头用一两句话回答“上一章留下了什么问题”，每章结尾回答“下一章为什么必须使用本章产物”；如果两章之间没有输入/产出关系，应合并或重排。
- 章节编号不是装饰。正文中首次出现的符号、命令、数据结构和 API 必须能在前文找到解释，或在本节先补桥。
- 课程首页的章节地图必须列出“前置输入 → 本章产出 → 完成证据”，不得只列主题名。

### 重要程度与篇幅

篇幅应按“出口所需的推理难度”分配，而不是按主题热度或章节数量平均分配：

- **基础概念**要慢：变量、文件、进程、函数、状态、版本、分支、向量等第一次出现时不能假定读者已知；
- **核心难点**要深：C 的内存/指针、线性代数的坐标变换、数据结构的不变量、网络的权威性、Transformer 的注意力等，可以拆成多章并包含多个实验；
- **低价值内容**要短：历史背景、工具菜单、名词清单和与出口无关的行业常识不应挤占正文；
- **长课允许长**：D3 的 C、数学、算法、系统和 AI 课程应像一门认真设计的教材，拥有足够章节、例题、反例、代码与渐进式实践；“章节少”不是质量目标。C 与线性代数至少应覆盖 12 个连续知识单元；机器学习与 LLM/Transformer 至少应覆盖 12 个连续知识单元，除非课程地图明确证明可以合并。

## 三、初学者友好的页面写法

- 首段先说“你将观察到什么问题”，不要先给抽象定义；
- 首次出现术语时，用一句普通话解释，再给正式定义；
- 代码逐行解释关键行，说明输入、输出、状态变化和如何运行；
- 命令必须说明“它读取什么、改变什么、不会改变什么、成功/失败如何判断”；
- 每个长页面在结尾写“现在你应该能解释/运行/诊断什么”；
- 对容易混淆的概念成对比较：工作区 vs 暂存区、缓存 vs 产物、merge vs rebase、位置 vs 方向、训练集 vs 测试集；
- Mermaid/图表必须有文字结论，不能让颜色或箭头承担唯一解释。
- 命令教学必须写清：读取的状态、改变的状态、不会改变的状态、成功信号、失败信号、共享历史/数据风险和恢复动作；不能用一张命令速查表代替过程教学。

## 四、课程形态建议

| 课程形态 | 推荐主线 | 必须出现的证据 | 不应强套 |
|---|---|---|---|
| 数学/理论 | 问题 → 建模 → 推导/证明 → 反例 → 数值实验 | 符号含义、推导、边界、误差和实验 | 每节硬塞引擎 API |
| C/数据结构/算法 | 需求 → 表示 → 不变量 → 实现 → 复杂度 → 基准 | 内存、所有权、复杂度、测试和失败 | 只抄标准实现 |
| 系统/底层 | 现象 → 机制 → 观测 → 测量 → 诊断 | 命令、日志、计时、资源和故障证据 | 架构口号 |
| 架构/软件工程 | 变化轴 → 状态/依赖 → 方案比较 → 演进 | 所有者、生命周期、接口、测试和回滚 | 唯一模式论 |
| 引擎/工具 | 最小场景 → 生命周期/API → 调试 → 项目化迁移 | 版本边界、调用时机、失败路径 | 菜单/API 清单 |
| AI/机器学习 | 数据/任务 → 表示 → 模型 → 训练/推理 → 评估 → 部署 | 基线、损失、数据切分、指标、失败和成本 | 只讲模型名词 |
| 生产/发行 | 交付目标 → 风险 → 流程 → 验收 → 回滚 | artifact、证据、权限、兼容性和 runbook | 大段行业常识 |

## 五、Git、AI 与现代技术的特别要求

### Git 与团队协作

Git 相关课程不能只列命令。每个命令至少说明：

- 它观察或改变哪个状态（工作树、暂存区、本地提交、远端引用）；
- 它的输入、输出和退出条件；
- 它是否重写历史，是否适合共享分支；
- 常见错误、恢复方法和验证命令；
- 在专业团队中由谁在什么阶段使用。

协作正文必须覆盖一条完整链路：任务拆分 → 分支命名 → 小提交 → 本地检查 → push → Pull Request/MR → CI → review → merge → 集成分支验证 → 发布候选 → 正式发布 → 事故回滚。要区分小团队 GitHub Flow、需要发布分支的 Git Flow 变体和大规模 trunk-based development；公开案例与教学推断分开，不声称某家公司内部唯一做法。

### AI 与机器学习

AI 课程要把“AI”拆成可学习的层次：

1. 线性代数、概率和优化如何成为模型的语言；
2. 数据、特征/表示、模型、损失、梯度、训练、验证、测试和推理的关系；
3. 神经网络、反向传播、注意力、Transformer、token、embedding、预训练、微调、RAG、工具调用和评估；
4. 游戏中的 NPC 决策、玩家建模、程序化内容、对话、资产/测试/工具辅助和端侧推理；
5. 数据许可、隐私、提示注入、幻觉、延迟、显存、成本、确定性和人工审核。

每个 AI 结论都必须有可运行的小模型、公开数据/合成数据、基线、指标和失败案例；不能把调用一个黑盒 API 伪装成理解模型。涉及快速变化的库/API 时记录版本与访问日期，正文优先稳定原理。

## 六、实践与评估

- 每门课最多 1 个主实践 + 2 个微实验，这是上限而非配额；
- D3 课程可拥有更多章节与小练习，但不要把多个没有独立验收标准的练习包装成多个实践；
- 题目少而精，题面、最小提示和折叠答案默认同页；
- 每题必须有参考答案/方案、推理、边界、常见错误、验证方法和游戏映射；
- 实践必须说明独立最小版本、代码入口、运行命令、验收、故意失败、回滚点和主项目冒烟；
- 不要求学习者填写进度、日志、错题本或决定记录，学习证据由命令输出、测试、测量、推导和运行结果承担。

## 七、研究、版本与公开边界

优先官方文档、标准、论文、源码和大学教材；记录版本、访问日期、用途、限制、不确定性和是否进入正文。不要捏造大厂内部做法，不复制商业项目源码/文档/素材，不提交个人信息、秘密、缓存、机器路径或未审查生成内容。
