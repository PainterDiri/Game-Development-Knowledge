# 章末出题人规范

## 目的

章末练习不是章节装饰，也不是固定数量的检查项。学习者应在合上正文后，通过一个**可以判定的产物**证明自己能解释、预测、计算、修复、推导、设计、实现或操作本章刚建立的能力。出题人与正文作者依次切换角色，是为了避免把“正文提到过”误判成“已经能独立使用”，也避免用重复的短问答填满页面。

## 先做证据蓝图，再写题

正文完成后，出题人先列出本章的 2–6 个核心产出，并为每个产出回答：

1. 学习者需要记住什么，还是需要现场推出来？
2. 哪个输入、状态、代码、数据或失败场景能暴露误解？
3. 学习者最终交付什么：数值、状态表、命令序列、补丁、测试、证明、设计图还是解释？
4. 什么观察能判定正确，什么常见错误必须被区分？
5. 这是正文示例的原样复述，还是换过输入、约束或场景的迁移？

题目必须以正文已经教过的机制为依据；不能偷偷要求下一章的术语、未公开代码或个人学习记录。出题人可查阅可靠教材、大学课程、标准、论文、官方文档中的题型与常见误解，但不得复制题面、答案或数据。

## 题量由覆盖决定，不由模板决定

| 本章情况 | 常见题量 | 设计重点 |
|---|---:|---|
| 过渡、诊断或单一窄概念 | 1 | 留下一题即可暴露核心误解 |
| 一个主要机制加一个边界/失败 | 2–4 | 至少有一次推演/操作和一次修复/迁移 |
| 多个相互依赖的机制 | 4–8 | 按依赖拆分，避免一题塞完所有能力 |
| 数学、算法、证明、统计或综合计算 | 视需要可超过 8 | 分开练计算、证明、反例、建模和迁移 |

这只是设计参考，不是自动门槛。少题必须因为概念窄而少，多题必须因为有独立能力需要取证而多。不得为了通过检查注水。

## 题型库：按知识选，不追求表面花样

- **单选/多选/判断并纠错**：选项必须对应真实误解；答案要逐项解释，不能只给字母。
- **排序/配对/填状态表**：适合 Git 状态、调用栈、协议阶段、生命周期、流水线与依赖图。
- **预测与代码追踪**：给出完整小输入、关键代码和初始状态，要求写出输出或逐步状态。
- **计算与估算**：给定单位、精度、边界和舍入规则，要求展示过程；适合数学、内存、带宽、概率与帧预算。
- **证明与反例**：明确命题、假设和允许使用的结论；不能把“我觉得”当证明。
- **故障诊断与最小修复**：给日志、diff、堆栈、网络包、性能数据或故意错误代码，要求定位首个因果缺陷、提出最小修复和回归测试。
- **短代码/API/测试题**：限定语言版本、函数签名、允许修改范围、错误契约和测试入口；答案必须可编译、可运行或明确标为伪代码。
- **命令/引擎实作题**：给初始状态、工作目录、操作目标、禁用动作、预期 UI/命令输出和恢复路径；不把“自行建项目”当指导。
- **设计与取舍题**：提供负载、生命周期、信任边界、失败成本和备选方案；用约束评分，不能只问开放感想。
- **迁移题**：把同一机制换到 Unity、UE、服务器、MOBA/FPS 或肉鸽系统，要求指出哪些不变量保留、哪些环境假设改变。

题型多样不是每章强塞所有形式。若章节教的是可执行技能，至少有一道题要求实际命令、代码、计算、状态推演或故障诊断，不能整章只剩短主观问答；纯理论章节也应通过证明、反例、建模或精确推演取得证据。

## 题面必须自带判定条件

每题紧邻标题写出：

- `**题型**`：从上面的能力类型中选最贴切的一种或两种；
- `**作答产物**`：明确学习者要交付的东西和格式；
- 必要时给语言/引擎/工具版本、初始状态、固定输入、可修改范围和禁止动作。

不要写“谈谈理解”“写一个验证”“设计一下系统”这种无法判定的题。应改成“给出三字段状态表”“补全函数并通过四个列出的用例”“在临时仓库执行命令并保存指定输出”“在给定负载下计算上界并选择方案”。

## 不生成提示

课程不再生成“最小提示”、逐级提示或隐藏解题路线。卡点应通过以下方式解决，而不是在答案前再放一个半答案：

1. 把缺失前置补回正文；
2. 把题面中的输入、约束、术语或交付格式写清；
3. 将过大的综合题拆成能独立判定的小问；
4. 在完整解析中解释错误思路，再让学习者更换输入重做。

主实践仍可有分阶段指导，因为它承担长任务的脚手架；章末题不使用提示折叠块。

## 完整解析与评分点

每题只保留一个紧邻题面的 `<details><summary>讲解、判定与验证</summary>`。解析至少包含：

1. 推理或操作链，而不是只有最终数字、选项或代码；
2. 明确评分/判定点，说明什么算完整、部分正确和错误；
3. 成立条件、边界与至少一个常见错误；
4. 可执行验证、手算复核、反例或观察方法；
5. 具体游戏工程映射。纯数学题说明它如何影响变换、相机、瞄准、碰撞、概率、网络预算或性能决策。

存在多个正确实现时按约束评价，不伪装成唯一写法。代码答案标明完整程序、可链接函数、依赖前文片段、补丁或伪代码；命令答案说明当前目录和会改变的状态。

推荐格式：

```markdown
## 本章练习

### C04-Q1：循环边界状态表

**题型**：代码追踪 + 不变量证明
**作答产物**：填写每轮 `i/count` 状态表，写出终止条件，并给出一个越界反例。

题面、输入、约束……

<details><summary>讲解、判定与验证</summary>

推理链、评分点、边界、常见错误、验证和游戏映射。

</details>
```

## 删除、合并与重写标准

候选题有以下问题时直接返工：

- 只复述定义、标题或正文原句；
- 与另一题暴露同一误解且答案路径相同；
- 只要求“写证据/谈收获”，没有固定输入、约束和判定点；
- 答案必须依赖下一章、隐藏代码或个人记录；
- 所有题都只是简短解释，没有计算、推演、修复、实现或操作证据；
- 游戏映射只是附加一句“可用于游戏”；
- 题目大到完整答案必须引入本章未教的新系统；
- 答案只有结论，没有推理、边界和验证。

## 三角色走查

### 出题人审题

1. 每个核心产出是否至少被一道题直接检验？
2. 题型是否由知识决定，而不是统一模板？
3. 是否至少有一道题能暴露本章最危险的误解或失败？
4. 题面是否给足输入、约束、作答产物和判定条件？
5. 是否删掉重复、纯复述和无法判定的主观题？

### 求知者走查

合上解析实际作答：命令要在一次性临时目录执行，代码/计算要走完整过程。检查是否必须猜目录、版本、符号、API 状态或隐藏前置；若必须猜，返工正文或题面。打开解析后检查它是否能解释自己的错误，而不只是宣布答案。

### 专业审查者复核

检查答案的机制、边界、复杂度、生命周期、数值、信任边界和版本是否正确；代码/命令是否可复现；评分点是否与题面一致；游戏映射是否真的改变工程决策。角色走查由同一执行者依次完成时必须如实说明，不能冒充独立教师或真实学习者反馈。
