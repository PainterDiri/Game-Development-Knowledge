# 教学覆盖与证据：从“看过”走向能独立解决问题

本规范用于生成一门课或修订已有内容，不授权批量生成课程，也不增加学习者档案。目标是专业教育级的知识覆盖与可理解的推理，不是更多标题、更长正文或“换一个模型再写一遍”。以下是本仓库的教学设计要求，不是某大学的认证标准。

## 1. 先明确课程承诺，再判断遗漏

在课程 README 的地图中，为每组核心能力写出：

| 能力 | 需要的前置 | 正文教在哪里 | 不看解答能完成什么 | 证据与限制 |
|---|---|---|---|---|
| 示例：解析不可信整数 | 数组、字符、函数调用、输出参数补桥 | 文本解析章节 | 拒绝尾随垃圾、负值与越界，并保留原状态 | 边界输入、错误码、状态前后比较；不等于完整网络协议解析 |

不是每个 API 都填一行，而是每个能被独立误解的核心机制有落点。生成者先与相关标准、公开大学课程或教材目录核对覆盖：遗漏了什么、为什么取舍、由哪门课承接。不能只核对旧正文，因为旧正文的遗漏不会自己出现在目录里。

- **核心必学**：必须有解释、完整例子、独立判断题和验证；不得挪到“拓展”逃避出口承诺。
- **补桥**：当前任务立即会用，但前置课尚未教会。给最小语义、一个推演和一道诊断，再指向正式章节。
- **后续深化**：本章不要求独立完成；明确承接课程、进入条件和当前禁止作出的推断。
- **参考查阅**：完整开关表、平台枚举等不必逐条背诵，但要教会查找和验证的方法。

不要承诺“一门课讲完所有细节”。承诺应是核心范围无隐含跳步、边界明确、遗漏可追踪，而不是无限膨胀。

## 2. 教知识点，而不是解释一个名词后立刻出题

对每个核心机制，按适合该领域的顺序组织：

1. 展示具体输入和问题，让读者先预测；
2. 解释第一次出现的符号、单位、术语和操作；
3. 用逐步状态表、数值推导、对象图或完整执行轨迹建立模型；
4. 给一个仅改变关键条件的反例，说明原结论为什么失效；
5. 让读者补完一个有约束的缺口，再独立完成不同情境的题；
6. 验证并解释证据不能证明什么。

不强制六个小标题。数学重推导与条件，算法重正确性与复杂度，系统重状态与测量，网络重故障与信任，架构重约束比较，引擎重生命周期与观察。不能在完整文章后反复追加“进一步拆解”来凑深度；应把重复内容合并进原来的因果链。

C 中先用到 `&out`、`char *end` 时，就教清“取地址、指针变量、通过地址回写”在该例中的作用，不能因为第 9 章讲指针就让第 8 章读者猜。类似地，不得在尚未教极限时突然要求误差证明，或把 C#、Python、C++ 当成已经掌握的通用前置。

## 3. 练习检验理解，不检验记忆原段落

出题前把核心误解列出来。优先采用预测、反例、计算/证明、定位失败、受约束实现和迁移取舍。每题写清输入、允许假设、成功标准；涉及平台相关结果时允许回答“不能确定”，但必须指出缺少什么条件。

- 删除“题 1 问怎么写复现脚本，题 2 只换故事再问一次”的重复。
- 完整解析必须展示关键中间步骤；“注意溢出”“用测试验证”不是解答。
- 至少有适合本课的迁移任务：例如把 CLI 的边界验证迁移到服务端协议入口，但不要求学习者先会 socket 编程。
- 后续章节可用一个已教机制解新问题，形成间隔复用；不是另建题库或要求学习日志。
- 一次题答对不能证明长期掌握。建议隔一段时间不看解答重新解释关键机制，但不记录到公共索引。

同一 AI 依次切换出题、求知和专业审查视角时，应如实称“角色走查”，不能冒充独立人员/真实学习者实验。

## 4. 示例、主实践与测试必须说同一种规则

每段代码标明是完整程序、可链接函数、依赖前文的片段、伪代码还是故意失败。写清文件位置、依赖、命令和预期现象。参考实现“简化”只能省去已声明不支持的功能，不能违反核心教学契约。

验收至少区分：

- **构建证据**：指定工具和开关编译通过；不证明业务正确；
- **样例证据**：该输入产生预期输出；不能推广到任意输入；
- **性质测试**：在实际枚举/生成的范围检查不变量；不是数学证明；
- **推导/证明**：在明确假设下成立；实现仍需核对；
- **动态诊断**：检测本次执行路径上的部分错误；没有报告不等于没有 UB；
- **性能证据**：限定环境、负载、次数与噪声；不能由一次更快推出普遍更快。

失败原子性应比较字段或规范化状态；短 checksum 相同只能辅助诊断，不能排除碰撞。不能用结构体 `memcmp` 替代语义字段比较，因为填充字节不属于业务状态。

可破坏的验证只在新建临时副本运行；不得覆盖学习者既有实践。构建/清理命令必须先证明操作范围，拒绝源目录、任意外部目录、符号链接和未知文件。测试不仅跑领域模块，也要覆盖用户真实入口、非法输入、恢复后的下一条合法操作。

## 5. 游戏贴合不能缩窄计算机科学

Unity 与肉鸽用于降低问题理解成本，不替代理论。每门课根据机制选有意义的映射，不强迫每章同时讲所有游戏类型。

后续逐课生成时，以下能力不能因为单机纵切片暂时不用就从总体系中消失：

| 能力范围 | 主要承接课程 | 需要留下的出口，而非只提名词 |
|---|---|---|
| 语言与内存 | C、OOP、语言原理 | 生命周期、所有权、错误处理；OOP 中显式补 C#，UE 前显式补 C++ 与 RAII |
| 数学与物理 | 线性代数、微积分与概率、图形、引擎 | 变换推导、数值误差、积分稳定性、碰撞与约束；不能只会调引擎 API |
| 算法与计算理论 | 离散数学、数据结构、算法、编译 | 不变量、复杂度、图搜索、自动机、不可行问题的边界 |
| 系统与并发 | 组成、操作系统、优化 | 内存层级、进程线程、同步、死锁、调度、测量与回归 |
| 实时多人 | 网络、在线服务 | TCP/UDP 边界、权威状态、tick、插值/预测/校正、乱序丢包、带宽预算、重连 |
| 持久在线世界 | 数据库、在线服务 | 事务、幂等、防重放、复制、一致性、分区/分片、崩溃恢复与容量评估 |
| 安全与运维 | 软件工程、网络、在线服务、发行 | 身份与授权、输入限额、凭据隔离、可观测性、负载测试、降级与恢复演练 |
| 产品与人机交互 | 资源、Unity 生产、发行 | 输入反馈、可访问性、可用性测试、内容迭代、平台与版权边界 |

在线服务可以不阻塞第一版单机游戏，但对“掌握多人服务端”的目标不能是只读选修；其唯一主实践应包含故障注入与恢复验收。一个本地双客户端原型不能被称为已经验证 MMO 规模。不要为了覆盖表立刻生成这些课程：在对应课程的生成任务中落实。

## 6. 发布与重审的诚实边界

保留 `completed` 的既有“公开内容发布”含义；不能把历史发布状态当成本轮全部重审通过。修订任务报告具体文件/知识点、复现缺陷、修改、实际测试和仍未检查的范围。若核心错误尚未修复，应明确警告或暂停相关内容的可用声明。

覆盖表与维护审计属于公开课程质量元数据，不记录学习者身份、位置、答案或能力评级。不加每页固定字数/章数指标，不以关键词替代人工判断；结构检查可以保留为预警，但不能给课程自动颁发“专业水平合格”。
