# 知识集现状审计与优化方案

> 审计日期：2026-08-23。本文只评估仓库公开源文件和自动门禁，不推断任何学习者的个人进度。

## 一、先给结论

当前仓库的**规范、路线设计和课程生产基础已经成形，但绝大多数课程仍未生成完整正文**。因此现在更准确的定位是“一个质量要求较高的课程生产骨架 + 2 门可学习课程”，还不能称为全面可学的游戏开发知识集。

- 课程总数：27 门；
- 已完成并可学习：2 门（工具链与 Git、C 程序设计）；
- `scaffolded` 准备中：25 门；
- 课程级正文页：工具链课程 9 页、C 课程 14 页，其余课程目前没有正式正文页；
- 课程级题目/答案与实践：工具链与 C 课程已有，其余课程尚未形成可验收闭环；
- 自动检查：通过。这个结果证明结构、链接、隐私和已完成课程的最低门禁有效，**不证明 25 门准备中课程已经具备学习价值**。

### 客观评级

| 维度 | 评级 | 证据与判断 |
|---|---|---|
| 路线覆盖面 | A- | 已覆盖 C、数学、算法、系统、工程、图形、AI、引擎、网络、优化和发行。 |
| 路线可执行性 | B- | 有阶段、前置和主实践，但 27 门线性顺序容易让学习者误以为必须先完成所有拓展课才能做出纵切片。 |
| 已发布教学内容 | D | 仅工具链课程有完整正文、实践、题目和下载包；其余是课程定位或研究入口。 |
| 零基础可学性 | C | 工具链课程表现良好；多数课程缺少诊断、逐章输入/产出、补桥、可运行示例和章末练习。 |
| 专业深度 | C（潜力 A） | 元数据和规范明确要求机制、失败、验证和游戏映射，但尚未在大多数课程中兑现。 |
| 实践闭环 | C- | 每门课程应有独立最小实践、验收证据和回滚/清理路径；目前只有已发布课程形成闭环。 |
| 维护可持续性 | B+ | 生成、同步、检查、下载包和本地阅读进度的基础设施较好；需要增加“内容健康度”审计，避免结构门禁掩盖内容空洞。 |

## 二、已经做对的事情

1. **把内容状态和学习者状态分开**：`completed` 表示公开课程已通过门禁，不冒充学习者完成度；阅读位置只保存在浏览器本地。
2. **把课程主实践机器可读化**：`practiceProject` 明确每门课唯一的独立实践名称；不再要求前置课程维护最终肉鸽项目接缝，完整项目由专门课程集中推进。
3. **工具链课程形成了可复用样板**：它从终端、Git 状态、协作、构建、复现、诊断到发布回滚，已经具备完整的“正文 → 实践 → 评估 → 契约 → 下载包”闭环。
4. **规范明确反对模板化堆页**：要求从现象开始，给出机制、不变量、失败、验证和游戏映射；D3 的 C、线性代数、系统和 AI 不能压缩成名词表。
5. **隐私、版权和构建边界意识较强**：公共知识、个人 `.practice/`、缓存、artifact、密钥和绝对路径的职责已经分开。

## 三、主要问题与影响

### 1. “课程总览很完整”与“实际能学”之间存在巨大落差

大多数目录只有 `README.md` 课程定位，尚未生成详细正文。它们可以通过 `scaffolded` 规则，但学习者打开后不能完成：

- 10–30 分钟诊断；
- 从具体现象到正式模型的连续学习；
- 可运行代码、推导、测量或故意失败；
- 题目、提示、解析和验证；
- 独立主实践及 Git 隔离。

**优化原则**：继续允许骨架存在，但在课程总览中明确显示“可学习/准备中”；完成课程前不得把状态改成 `completed`。每次只推进一门课，下一门是 `c-programming`。

### 2. 27 门课被默认呈现为一条长直线

编译原理、LLM、生成式 AI、UE 和在线服务对基础纵切片很有价值，但不是做出第一版单机 2D 肉鸽的必要前置。若不分层，学习者会在进入战斗、房间和内容生产前先被迫完成多个方向拓展，反馈周期过长，容易失去主线。

**优化原则**：保留完整培养方案，但区分：

- **核心主线**：完成基础纵切片与发行所需；
- **支撑课程**：强烈推荐，解决系统、数据、网络或 AI 扩展问题，但可在纵切片后补；
- **方向拓展**：面向引擎、编译、UE、LLM/生成式 AI 等专项迁移，不阻塞基础项目。

这不是降低标准，而是把“全面”从“所有内容一次性线性完成”改为“核心能力闭环 + 可解释的分支出口”。

### 3. 前置关系还没有完全变成可操作的学习契约

索引已经记录 `prerequisites`，但多数课程首页还没有把前置转换为：

- 学习者要能做的最小任务；
- 失败时补哪一个概念；
- 这一章的产物如何进入下一章；
- 完成证据是什么。

**优化原则**：每门课正式生成时，README 必须有逐章表格：`前置输入 → 核心问题 → 产出 → 完成证据 → 下一章用途`。没有这张表，只能是 `scaffolded`。

### 4. 课程主实践需要独立交付

每门课的主实践都必须有对应的最小版本、指导、代码或数据、故意失败和验收；只有课程名称或未来项目方向，不能支撑自学。工具链与 C 已形成两个可复用样板，其余课程仍待建设。

**优化原则**：每门课只有 1 个主实践；正文中的短实验放回章节。实践优先验证课程机制，不为了“像游戏”强行创建 Unity 工程，并说明输入/输出、状态拥有者、故意失败、验收、清理和 Git 隔离。

### 5. 自动门禁对骨架很宽松，容易让维护者误读结果

当前 `check_repo.py` 的成功输出主要说明结构正确。它对 `scaffolded` 课程不要求正文、题目和实践，这是合理的发布策略，但输出若只写“CHECK OK”容易造成“全部课程已就绪”的错觉。

**优化原则**：检查输出明确报告 `published` 与 `not-yet-published` 数量；课程索引增加路线角色和主实践路线；审计页记录内容健康度，而不是让结构门禁承担教学质量判断。

## 四、优化后的学习路线

### 核心主线（先形成可玩、可测、可发行闭环）

以下课程标记为 `curriculumRole: core`，其中 `practiceRequired: true` 的课程是核心路线建议完成的课程；其余核心课是强烈建议，但可按实际问题插入。

```text
工具链与 Git
  → C / 离散数学 / 线性代数
  → 数据结构 / OOP
  → 软件工程
  → 图形学 / 资源管线
  → 游戏 AI / 引擎架构
  → Unity 肉鸽生产
  → 优化、调试与工具
  → 发行与毕业项目
```

微积分与概率、计算机组成、操作系统、数据库和高级算法仍保留在核心知识面中，但不再作为“第一次可玩纵切片”的硬阻塞；它们应在对应问题出现时学习并导出测量、数据、性能或稳定性证据。

### 支撑课程（扩展能力，不阻塞基础纵切片）

- 计算机网络：理解通信、延迟和协议，为在线服务做准备；
- 机器学习基础：建立数据、表示、模型、损失、更新、评估和部署的可解释主干；
- LLM 与 Transformer：理解现代序列模型的机制和成本边界；
- 生成式 AI 游戏工程：重点放在许可、评估、缓存、回退和人工审核；
- 游戏网络、服务端与在线服务：在单机主线稳定后做旁路原型。

### 方向拓展（完成主线后选择）

- 编译原理与 DSL、编程语言与脚本：面向工具、配置语言、编辑器和运行时扩展；
- Unreal Engine Gameplay Programming：以 Unity 已有系统为参照做迁移，不作为 Unity 主线前置。

## 五、内容生产优先级

### P1：立即建设

1. `discrete-mathematics`：下一门课程，打通逻辑、集合、图、关系和规则验证；
2. `linear-algebra-for-games`：直接支撑变换、碰撞和战斗空间；
3. `data-structures` 与 `object-oriented-programming`：为可测试运行时和玩法模块提供实现基础；
4. `software-engineering`：把前面的小实验汇入稳定工程；
5. `game-engine-architecture`、`game-ai`、`unity-roguelite-production`：尽早形成可玩纵切片。

### P2：在主线出现问题时建设

- 微积分与概率：随机、插值、采样、统计验证出现时；
- 高级算法：路径规划、空间索引、调度或大规模内容出现时；
- 组成与操作系统：帧预算、内存、线程、加载和平台问题出现时；
- 数据库、图形学、资源管线、优化：存档、渲染、内容生产和性能问题出现时；
- 发行与毕业项目：核心循环冻结后开始，不提前创建“空发行课”。

### P3：主线稳定后的专项分支

- 编译/语言、ML/LLM/生成式 AI、UE、在线服务。

## 六、每门课程的完成定义

课程只有同时满足下列条件，才能从 `scaffolded` 变为 `completed`：

1. README 是课程首页和地图，而不是课程宣传语；
2. 有零基础诊断或补桥，并明确前置出口；
3. 正文按真实概念依赖组织，每个核心知识块包含机制、例子、失败/取舍、验证和游戏映射；
4. 至少有一个独立可判定的实践或明确说明为何合并到正文验证；
5. 题目、最小提示、解析、边界、常见错误和验证一一对应；
6. 版本敏感来源在相关章节就地标注版本、访问日期、用途与限制；
7. 运行同步、仓库检查、`git diff --check` 和 MkDocs 严格构建；
8. 人工完成一次零基础审查和一次专业深度审查；
9. 主实践不要求接入最终项目，公开代码只读，个人修改不会出现在主仓库提交中。
