# 3. Git 与资产协作：历史、引用和不可合并的文件

## 3.1 Git 不是文件同步器

Git 的核心不是“远端有一份文件”，而是对象和引用组成的历史图：

- **blob**：文件内容对象；
- **tree**：目录到文件/子目录对象的映射；
- **commit**：指向一个 tree、父提交和提交元数据的快照对象；
- **reference（引用）**：给某个提交起一个可移动或稳定的名字，例如分支和标签。

工作区、暂存区和提交是三个不同状态：

```text
工作树 --git add--> 暂存区 --git commit--> 本地提交 --git push--> 远端引用
```

因此：

- `git add` 选择下一次快照，不是上传；
- `git commit` 建立本地历史，不是测试通过；
- `git push` 推送对象和引用，不是发布成功；
- CI、artifact 和部署必须有自己的证据。

这个区分直接映射游戏团队：一个提交可以包含“伤害公式变更”，但只有 CI 构建、测试和冒烟通过，才有理由进入可试玩 artifact。

## 3.2 为什么提交要“单一目的 + 可验证”

适合协作和回归的提交不是按行数小，而是按原因边界小。一个好提交通常：

1. 只服务一个变化轴；
2. 包含该变化所需的代码、配置和测试；
3. 能在当前工程约束下构建或明确说明不能构建的原因；
4. 回退时不会同时撤销不相关内容；
5. 提交消息能指出验证命令。

例如，把“替换输入系统”“升级包”“重排场景”“修复退出码”塞进一个提交，会让 bisect 只能告诉你“这一大坨有问题”。拆开后，历史才能成为诊断工具。

## 3.3 merge、rebase、revert、reset 的选择

| 操作 | 改变什么 | 适用场景 | 共享主线风险 |
|---|---|---|---|
| merge | 新增合并提交，保留两条父历史 | 合并已经存在的分支 | 需要解决语义冲突 |
| rebase | 重写提交父关系和提交 ID | 未共享分支整理历史 | 已共享后会让他人引用失效 |
| revert | 新增抵消变化的提交 | 共享主线安全回退 | 旧提交仍存在，复杂变更可能冲突 |
| reset | 移动当前引用，可改变可见历史 | 本地整理、撤销未共享提交 | `--hard` 可能丢工作，远端强推破坏协作 |

共享主线已经包含坏提交时，默认路径是：

```bash
git pull --ff-only
git revert <bad-commit>
python3 -m unittest discover -s code/repro-game/tests -v
git diff --check
git push
```

如果是密钥、隐私或法律内容，`revert` 只恢复未来状态，不能保证历史和缓存中没有泄露；必须轮换凭据并按仓库策略清理历史。

## 3.4 冲突解决不是“选左边”

文本冲突只是 Git 无法推断意图。游戏资产冲突还可能不显示为文本冲突：

- 两个人分别移动 Unity 资产，GUID 与引用关系发生语义变化；
- 两个 Blueprint/场景二进制文件无法三方合并；
- 一个分支删除了旧输入映射，另一个分支仍引用它；
- UE 插件版本更新后，配置键仍存在但含义改变。

可靠的冲突处理顺序：

1. 先看两边提交目的、资产所有者和依赖关系；
2. 尽量把可读配置、脚本和资产源拆出；
3. 对必须独占编辑的二进制采用锁定/签出或明确负责人；
4. 解决后执行导入、引用检查、最小场景加载和相关测试；
5. 把“为什么选这个版本”留在提交说明或变更记录中。

冲突标记消失只证明文件语法恢复，不证明运行时语义恢复。

## 3.5 Unity、UE 与二进制存储的决策

### Unity

`.meta` 与资产身份绑定，不能因为“看起来是自动生成”就随意忽略。文本序列化和可见元数据能帮助审查，但场景合并仍然要靠拆分职责、减少并行编辑和运行时验证。

### Unreal Engine

文本配置和源码适合审查；大量内容资产、插件二进制和派生缓存需要额外的容量、锁定和恢复策略。Perforce 类流程常见于高频二进制协作，但课程不把它当作唯一答案；应按团队规模、离线需求、审查需求和恢复成本选择。

### Git LFS

LFS 把大文件内容放到独立存储，在 Git 中保留轻量指针。它解决仓库存储效率的一部分问题，不自动解决：配额、带宽、备份、锁定、许可证、离线工作和新成员恢复。验收不是“指针提交成功”，而是干净 clone 能取得真实对象并让构建通过。

## 本章微实验：把历史变成证据

在临时目录中：

```bash
mkdir -p /tmp/git-lab && cd /tmp/git-lab
git init
printf 'spawn=3\n' > config.txt
git add config.txt && git commit -m 'Add spawn config'
printf 'spawn=0\n' > config.txt
git add config.txt && git commit -m 'Introduce invalid spawn'
git log --oneline --decorate --graph
git revert HEAD
cat config.txt
```

观察：`revert` 没有删除坏提交，而是增加一个新提交恢复内容。再尝试 `git diff HEAD^ HEAD`，理解“历史事实”和“当前状态”的区别。

## 本章结论

Git 的价值不只是备份，而是让变化有身份、让回退有语义、让二分有前提。资产协作的关键也不是选哪个工具，而是让身份、引用、锁定和冷恢复都能被验证。

## 3.6 不靠背命令：观察 Git 的三种状态

在临时仓库执行：

```bash
mkdir -p /tmp/git-state-lab && cd /tmp/git-state-lab
git init
printf 'damage=10\n' > combat.cfg
git add combat.cfg
git commit -m 'Add combat config'
printf 'damage=12\n' > combat.cfg
printf 'crit=0.1\n' >> combat.cfg

git diff                 # 工作树 vs 暂存区
git diff --cached         # 暂存区 vs HEAD
git diff HEAD             # 工作树 vs HEAD
git status --short
```

如果只记“`add` 后 commit”，会错过一个重要事实：暂存区是下一次快照的可编辑边界。游戏团队可以利用它把一个修复拆成“规则 + 测试 + 配置”三个可审查部分，也可能误把半成品加入提交。因此提交前要检查 `git diff --cached`，而不是只看 IDE 的变更列表。

Git 的对象关系也能直接观察：

```bash
git cat-file -t HEAD
git cat-file -p HEAD | head
git ls-tree HEAD
```

这里可以看到 commit 指向 tree，tree 再指向文件对象。这个模型解释了为什么提交是快照、为什么分支只是引用、为什么删除本地分支不等于远端历史消失。它不是要求你手写对象，而是让回退和恢复不再依赖魔法命令。

## 3.7 合并冲突的可验证流程

冲突处理应从“意图”开始，而不是从“选 ours/theirs”开始：

```text
1. 找出冲突双方各自要解决的游戏问题
2. 判断变更是否同一资产、同一 GUID、同一配置键或同一生成器版本
3. 先恢复可读源和元数据的一致性
4. 再做导入/加载/构建/冒烟
5. 只在验证通过后提交合并结果
```

对文本配置，保留两边意图可能意味着手工组合；对 Blueprint、场景或大型二进制资产，通常需要锁定/签出、资产负责人或从已知 artifact 恢复。冲突标记清空只能证明文本语法恢复，不能证明预制体引用、输入映射、材质参数或插件注册仍然正确。

一个实际的恢复清单：

```bash
git status
# 解决后先检查是否还有未合并路径
git diff --check
git diff --name-only --diff-filter=U
# 再运行最小导入/测试/构建命令
git add <已验证的文件>
git commit
```

如果存在 LFS，额外验证真实对象而不是只验证指针：

```bash
git lfs ls-files
git lfs pull
git lfs fsck
```

这些命令是否可用取决于团队安装和远端配置；LFS 不能代替备份、锁定、许可证记录或干净 clone 恢复演练。

## 3.8 何时 Git 不是唯一答案

选择 Git、LFS、Perforce 或混合方案时，比较的是约束：

| 约束 | Git + 文本化 | Git LFS | Perforce/锁定流程 | 混合方案 |
|---|---|---|---|---|
| 文本审查 | 强 | 强 | 取决于配置 | 可保持 |
| 大二进制吞吐 | 一般 | 较好但依赖服务 | 通常较好 | 按资产分流 |
| 离线工作 | 强（已获取对象时） | 受对象获取影响 | 取决于工作区 | 需明确边界 |
| 独占编辑 | 需额外约定 | 可加锁定 | 核心能力 | 资产分类决定 |
| 新成员恢复 | clone + LFS/依赖 | 需验证配额与带宽 | 需服务器权限 | 需要两套恢复文档 |

表格不提供“行业唯一答案”。小型 2D 纵切片可能用 Git + 文本化场景；大量二进制资产的团队可能需要锁定和集中式内容服务器。关键验收永远是：新成员能获取真实资产、能定位谁拥有冲突、能从提交恢复可运行构建。
