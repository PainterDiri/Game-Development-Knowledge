# 4. 调试与回归：把失败变成证据

## 从“坏了”到可判定命题

一个可调试的问题至少包含：

```text
版本/提交 + 平台/工具 + 输入序列 + seed/内容版本
+ 期望结果 + 实际结果 + 日志/截图/转储
```

日志不是把所有变量打印出来；它应包含时间或帧号、实体/房间 ID、事件类型、关键输入和版本标识，并避免泄露密钥/个人路径。断言（assertion）用于在不变量被破坏的第一现场停止或报告，例如“房间图必须可达”“manifest 的 commit 不能为空”。

## 最小复现与故障分类

1. **复现**：把输入缩到最短；固定 seed、平台和提交。
2. **隔离**：区分源代码、资产、工具版本、环境和缓存。
3. **观测**：增加结构化日志、构建 manifest、测试输出或崩溃符号。
4. **定位**：用测试、`git bisect`、二分关闭功能或最小场景找首个分叉点。
5. **修复并防回归**：把最小复现变成自动测试或构建门禁。

常见误诊：

- 清缓存后消失：可能是缓存污染，不代表缓存没有问题；需要冷构建回归。
- 只在 CI 失败：可能是路径大小写、工具版本、权限、无 GUI 或未安装平台模块。
- 只在合并后失败：优先检查冲突解决后的语义、资产引用和配置差异，不要立即指责 Git。
- 只在某个 seed 失败：这是高价值输入，应保留 seed，不能用“多跑几次”替代修复。

## `bisect` 的前提

二分假设好坏在提交序列上大致单调，且每个提交都能运行判定命令。若提交不可构建、测试不稳定、外部服务变化或工作树有未提交改动，结果不可信。可以用 `git bisect skip` 跳过不可判定点，但要承认定位精度下降。

## 游戏映射

- 肉鸽房间：记录 `runSeed`、房间索引、生成器版本和玩家输入；复现“第 7 房间没有出口”而不是复现整局。
- Unity：记录 Editor/Package 版本、场景路径、序列化资产差异和 Player.log；构建失败与运行时崩溃分开。
- UE：记录引擎版本、目标平台、Automation 测试名、日志类别和打包配置；不要把 `Saved/` 当作唯一诊断来源。
- 专业项目：构建产物要带符号或符号索引，崩溃报告引用提交和构建 ID，修复后保留回归测试。

## 验证：故意制造一个回归

在主实践中先让 `generate_room(seed)` 正常，再引入一个只在 seed 7 触发的错误。运行：

```bash
python3 -m unittest discover -s tests -v
```

测试必须失败且指出 seed；修复后把这个 seed 留在测试中。随后用两次提交演练 `git bisect run python3 -m unittest discover -s tests -v`。如果测试命令会修改工作树，先改为写临时目录或在命令中清理，否则二分会被副作用污染。

!!! note "验证结论"
    调试能力不是日志数量，而是能把失败压缩成一个可重复、可比较、可自动判定的实验。
