# 4. 游戏资产协作：Unity、Unreal 与二进制边界

## 资产不是“图片文件夹”

游戏资产常包含内容、导入设置、引用关系、压缩/平台变体和生成缓存。一个看似只改贴图的提交，可能同时改变材质、场景引用和构建大小。因此资产协作要问四件事：

1. **谁拥有源？** 原始 PSD、FBX、WAV、Blueprint 或脚本在哪里维护？
2. **谁拥有引用？** GUID、路径、插件注册和导入设置如何稳定？
3. **谁能修改？** 是否允许并行编辑，是否需要锁定/签出？
4. **如何恢复？** 新成员能否 clone、重新导入、得到相同内容并回滚？

## Unity 的迁移原则

- 把 `Assets/`、`Packages/`、`ProjectSettings/` 和资产 `.meta` 当成项目输入；
- 让序列化和元数据可见，便于审查和合并；
- 把 `Library/`、`Temp/`、`Obj/`、本地日志和构建输出视为可再生目录；
- 用 batch/headless 构建入口替代“某人点击菜单”；
- 记录 Unity Editor、Package、目标平台模块和许可证前提。

**失败案例**：只提交 `.unity` 场景而忽略 `.meta`，移动资产后 GUID 变化，预制体引用悄悄断裂。验证应包含引用检查和冷导入，而不是只看 Git diff。

## Unreal Engine 的迁移原则

- 提交 `.uproject`、源码、`Config/`、内容和插件配置；
- 通常不提交 `Binaries/`、`Intermediate/`、`Saved/`、`DerivedDataCache/`；
- 区分可读配置与二进制内容，按团队规模选择 Git LFS、Perforce 或其他方案；
- 用 Automation、命令行或 BuildGraph 让编辑器动作进入自动流程；
- 记录引擎来源、平台 SDK、插件和目标配置。

**失败案例**：只验证编辑器能打开，却没有验证 Shipping 配置能打包；结果缺少插件、输入映射或平台文件。打开项目是导入检查，不是交付检查。

## 二进制协作决策表

| 约束 | 适合的关注点 | 不能假设 |
|---|---|---|
| 少量二进制、个人项目 | Git 普通存储、清晰目录 | 大文件永远不会增长 |
| 大文件、需要 clone | Git LFS、配额、带宽、恢复 | LFS 自动备份 |
| 高频并行改大资产 | 锁定/签出、资产负责人、Perforce 类流程 | 文本 diff 能解决所有冲突 |
| 多平台导入缓存 | CI/runner 缓存 | 缓存是发布真相 |

## 迁移任务

为你的 Unity 或 UE 项目画一张表：

```text
路径 | 类型 | 拥有者 | 生命周期 | 是否版本控制 | 冷启动验证
```

至少填入 10 个路径，其中必须包括一个元数据文件、一个二进制资产、一个缓存目录、一个配置文件和一个构建输出目录。

## 小检查

- [ ] 我能解释 `.meta`/GUID 与普通缓存的不同；
- [ ] 我能为二进制资产选择存储/锁定策略并说明代价；
- [ ] 我能把 Unity/UE 的编辑器操作改写成命令、脚本或自动化测试；
- [ ] 我能为“新成员 clone 后资产引用断裂”设计验证。
