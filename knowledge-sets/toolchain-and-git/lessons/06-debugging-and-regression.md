# 6. 调试与回归：把失败压缩成实验

## 一份有用的失败报告

“游戏坏了”不是可判定命题。最小报告至少包含：

```text
commit/build ID
平台、引擎/工具版本
内容版本
输入序列
seed / room index / wave index
期望结果
实际结果
日志、断言、崩溃符号或最小截图
```

日志不是把所有变量打印出来；应记录能区分状态转移的字段，并避免密钥、用户目录和隐私信息。

## 四步最小复现

1. **固定**：提交、平台、工具、seed、内容版本；
2. **缩小**：从整局缩到一个房间、一个波次或一次导入；
3. **判定**：把失败变成非零测试或明确断言；
4. **保存**：修复后将最小输入变成回归测试。

对于 `seed=7` 的第 3 个房间，优先写：

```python
room = generate_room(seed=7, room_index=3)
assert has_exit(room)
```

而不是让测试重新跑完整游戏并依赖人工观察截图。

## bisect 的逻辑

`git bisect` 利用提交序列做二分搜索，但必须满足：

- 有已知 good 和 bad 提交；
- 中间提交大多可构建/可测试；
- 测试命令稳定、无交互、退出码明确；
- 外部网络、时间、随机和缓存不会改变结果；
- 工作树不会被测试污染。

如果某提交不可判定，使用 `git bisect skip`，并在结论中说明精度下降。

## 失败分类比“重试”更有价值

| 现象 | 第一怀疑 | 验证 |
|---|---|---|
| 清缓存后消失 | 缓存污染或未声明依赖 | 冷构建、比较 manifest |
| 只在 CI 失败 | 路径、权限、工具/平台模块 | 打印允许的版本清单和退出码 |
| 只在合并后失败 | 语义冲突、资产引用、配置 | 检查合并后的输入和导入结果 |
| 只在一个 seed 失败 | 算法边界或随机流 | 最小 seed 测试 |
| 产物能生成但不能启动 | 资源/平台/打包配置 | 产物冒烟和日志 |

## Checkpoint C

1. 在 `generate_room` 中故意让 seed=7、room=3 缺少出口；
2. 运行测试，确认失败信息包含 seed 和 room；
3. 通过两个提交引入/修复 bug；
4. 用 `git bisect run` 或手动二分定位；
5. 修复后保留回归测试，并在 CI 中执行。
