# 题目

默认流程：先心答/纸答，再展开答案；只在卡住时看最小提示。

### TOOLCHAIN-Q1：边界分类

一个 Unity 项目提交了 `Assets/`、`ProjectSettings/`、`Packages/`、`Library/` 和 `Build/`。请把它们按“源/元数据或配置/缓存/产物”分类，并解释为什么“删掉后能重建”比“通常这么做”更重要。再给出 UE 的对应思路。

### TOOLCHAIN-Q2：Git 语义与回退

提交 A 在主分支上，提交 B 已经推送并被其他人拉取；B 引入了玩家无法移动的回归。为什么共享主分支不应优先 `reset --hard` 后强推？请比较 `revert`、`merge` 和 `rebase` 在这个场景中的作用，并给出最小验证命令。

### TOOLCHAIN-Q3：复现差异

两次相同提交、相同 seed 的构建，`game.py` 相同，但 `build-manifest.json` 不同：一次写入了当前时间，一次写入了绝对工作区路径。这个构建能否称为可复现？如何修复，同时保留调试所需的信息？

### TOOLCHAIN-Q4：引擎迁移

一个团队说：“Unity/UE 项目太大，CI 不需要跑游戏，只要编辑器能打开即可。”请从工具链不变量、测试层次和失败成本三个角度反驳或限定这句话，并设计一个最小门禁。

### TOOLCHAIN-Q5：回归定位

只有 seed=7 的第 3 个房间生成了没有出口的地图。请设计一个从报告到修复的诊断路径，必须包含最小复现、日志字段、`git bisect` 的前提和最终回归测试。

### TOOLCHAIN-Q6：CI 安全与交付

CI 中有一个缓存步骤和一个 artifact 上传步骤。有人建议“把缓存当构建产物上传，并给所有 job 写权限，方便排错”。指出至少三处问题，并给出更安全的最小权限/证据策略。
