# 答案与解析

<details>
<summary>TOOLCHAIN-Q1 参考答案</summary>

**最小提示**：问“删掉后是否能由版本控制中的输入重建”。

**参考答案**：`Assets/` 是 Unity 的主要源/资产输入，资产旁的 `.meta` 是稳定引用所需的元数据；`ProjectSettings/` 与 `Packages/` 是项目配置和依赖声明；`Library/` 是本机导入缓存，通常可删除再生成；`Build/` 是产物目录，通常不作为源提交。关键不是死记目录表，而是验证：在干净 checkout、安装声明版本的 Unity 和平台模块后，删除 `Library/` 能否重新导入和构建。UE 同理：提交 `.uproject`、源码、`Config/`、内容和插件配置；通常不提交 `Binaries/`、`Intermediate/`、`Saved/`、`DerivedDataCache/` 等可再生目录。

**推理**：若删掉目录就无法构建，它可能不是缓存，而是未声明输入；若把缓存提交，仓库会变大且掩盖环境缺失。Unity 的 `.meta` 不能简单视为缓存，因为它参与资产引用稳定性。

**边界**：特定 Unity/UE 版本、插件和团队策略可能有例外；例外必须写进项目约定并经过冷构建验证。

**常见错误**：把所有二进制都提交；把 `.meta` 忽略；把“CI 能打开编辑器”当作构建成功。

**验证方法**：记录目录分类，复制干净 checkout，删除生成目录，运行最小测试/构建，并保存日志和 manifest。

**游戏映射**：场景 GUID 丢失会让 prefab/引用断裂；错误地提交缓存会让“本机能跑”的肉鸽房间在另一台机器失效。
</details>

<summary>TOOLCHAIN-Q2 参考答案</summary>

**最小提示**：共享历史的关键约束是别人已经引用了 B。

**参考答案**：不应优先 `reset --hard` 后强推，因为这会移动远端分支引用并改写其他人已经基于 B 工作的历史，造成丢提交和协作分叉。`git revert B` 产生一个新提交 C，内容抵消 B，历史仍可审查，适合主分支快速回退。`merge` 用于把两个分支的历史合并，解决并行变化；它不是专门回退坏提交的命令，但修复分支可以通过 merge 回主线。`rebase` 改写提交父关系，适合尚未共享的本地整理；对已推送并被使用的 B 不应作为默认修复手段。

最小验证：

```bash
git switch main
git pull --ff-only
git revert <B>
python3 -m unittest discover -s tests -v
git diff --check
git push
```

**推理**：修复的目标是恢复行为并保留可追溯性，而不是让提交图看起来漂亮。

**边界**：如果 B 含敏感信息或必须从所有历史移除，需使用专门的历史清理流程、权限处理和团队停工窗口；那不是普通回滚。

**常见错误**：把 `revert` 说成删除提交；用 `reset --hard` 清理冲突前未保存工作；只验证源码编译不验证玩家移动。

**验证方法**：确认 C 在 B 之后，运行回归测试，检查远端分支没有被强制改写。

**游戏映射**：发布线可回滚到已验证 artifact；主线用新提交撤销坏的碰撞/输入改动，后续再以独立提交修复。
</details>

<summary>TOOLCHAIN-Q3 参考答案</summary>

**最小提示**：区分“调试信息有价值”和“它是否是确定性输出”。

**参考答案**：若把整个 manifest 当作构建输出，两次内容不同就不能称为完全可复现；但这不表示必须丢掉时间和机器信息。修复方式是把字段分层：`deterministic` 区域只放提交、工具版本、seed、相对输入路径、哈希和配置；`provenance` 区域可放构建开始时间、CI run ID、机器/工作区信息，并明确它是非确定元数据。绝对路径应归一化为仓库相对路径或稳定标识，避免用户名和机器目录泄露。

**推理**：可复现性要求相同输入得到等价确定结果；调试来源追踪要求知道“在哪一次构建、在哪台 runner 上发生”。两者可以通过字段边界并存，不能把非确定字段伪装成内容哈希的一部分。

**边界**：如果发布系统要求对整个文件做哈希，就对确定性 manifest 计算内容哈希，另存 provenance；或定义比较器忽略明确列出的字段。不可声明地忽略差异是不合格的。

**常见错误**：用当前时间做随机种子；只删除时间却保留绝对路径；说“manifest 不重要所以可以不同”。

**验证方法**：两次构建 `diff`；分别比较 deterministic/provenance；改变 seed 或版本，确认只发生预期变化。

**游戏映射**：肉鸽运行报告需要 run seed 和内容版本；构建时间可帮助追踪发布，但不应改变房间生成或可比的资产清单。
</details>

<summary>TOOLCHAIN-Q4 参考答案</summary>

**最小提示**：编辑器能打开只覆盖很窄的路径。

**参考答案**：从不变量看，打开编辑器不能证明版本控制中的源、元数据、依赖、平台 SDK 和构建命令能产生产物；从测试层次看，至少要有脚本/单元测试、资产引用或导入检查、构建冒烟和目标平台启动检查；从成本看，越晚发现越贵，打包后才发现缺场景/插件/输入映射会浪费 runner 和人工测试时间。原话可以被限定为“每个 PR 不必都跑所有平台的完整 Shipping 构建”，但不能省略低成本门禁。

最小门禁：

1. 干净 checkout，锁定 Unity/UE 版本和依赖；
2. 快速单元/自动化测试；
3. 无交互构建一个 Development/测试配置；
4. 启动或加载最小场景，检查退出码、关键资产和日志无 Error；
5. 上传 manifest、日志、测试报告和失败时的诊断文件；夜间或 release job 再跑完整平台矩阵。

**推理**：CI 的目标不是每次都最大化成本，而是在不同反馈速度层级放置最有信息量的检查。

**边界**：需要授权/显卡/平台 SDK 的测试可能放在受控 runner；但应保留替代的静态、导入或无头验证，而不是以“环境难”为理由完全没有证据。

**常见错误**：只测编辑器启动；把缓存命中当构建成功；不保存产物导致无法手工复测。

**验证方法**：在干净 runner 或删除缓存后运行门禁，故意删一项依赖，确认它以非零退出码阻断。

**游戏映射**：Unity 的 Addressables/场景引用、UE 的插件和打包配置都应在构建前后被验证；肉鸽内容表缺失应在 CI 阻断而不是玩家首局发现。
</details>

<summary>TOOLCHAIN-Q5 参考答案</summary>

**最小提示**：先固定 seed，再问“从哪个提交开始坏”。

**参考答案**：

1. 从报告提取提交、平台/工具版本、内容版本、`runSeed=7`、房间索引 3 和输入序列；
2. 写最小复现：只调用 `generate_room(7, room_index=3)`，断言存在出口；
3. 增加结构化日志：seed、room index、generator version、入口/出口坐标、随机流状态或生成步骤计数、commit/build ID；避免把整局日志当作唯一证据；
4. 检查是否是输入数据/算法/资产/工具差异；先在已知 good 提交和当前 bad 提交运行同一命令；
5. 只有每个中间提交可构建、测试有稳定退出码、工作树干净且外部依赖固定时，才运行 `git bisect`；用 `git bisect run python3 -m unittest ...` 或专门的 seed smoke test；不可判定提交用 `skip` 并降低结论强度；
6. 修复后保留 seed=7、room=3 的回归测试，并检查其他 seed 的性质测试/统计边界；
7. 在 CI 中运行该测试，manifest 记录生成器/内容版本。

**推理**：最小输入提高定位信噪比；稳定自动判定才让二分有意义；把事故固定成测试才能防止下一次回归。

**边界**：如果生成算法本身允许多解，测试不应硬编码唯一地图，而应断言不变量（可达、出口存在、无重叠等）；如果随机库跨平台不同，锁定算法或比较行为级性质。

**常见错误**：用当前时间重跑；只看最后一张截图；bisect 前保留脏文件；修复后删除坏 seed 测试。

**验证方法**：最小命令在 good/bad 提交上给出稳定相反结果，修复提交通过，CI 复跑通过。

**游戏映射**：房间、掉落、敌人波次都可用 seed 复现；报告应定位到最小房间/波次而非要求玩家上传整台机器。
</details>

<summary>TOOLCHAIN-Q6 参考答案</summary>

**最小提示**：问“能否被删除”“是否是交付品”“谁拥有写权限”。

**参考答案**：至少有三处问题：

1. cache 是加速数据，可丢弃、可能来自旧输入，不应冒充发布 artifact；
2. 把缓存上传会放大存储、泄露路径/依赖或让人误以为它是可运行产物；
3. 所有 job 写权限违反最小权限原则，来自 PR/fork 的不可信代码可能获得生产能力；
4. 排错靠“更多权限”不等于更多证据，应该上传日志、测试报告、manifest、崩溃转储/符号索引等明确诊断材料；
5. 公开日志和 artifact 可能泄露密钥，不能打印环境变量。

更安全的策略：默认 `contents: read`；构建 job 只读 checkout 并使用缓存；构建结果、manifest、日志和报告作为 artifact 上传；只有受保护分支/标签的独立 deploy job 取得 Pages/发布所需权限；秘密通过平台 secret 注入并避免打印；第三方 action 锁定并审查版本/提交。

**推理**：权限、加速数据、交付物和诊断证据是不同边界，混在一起会同时扩大攻击面和排障噪声。

**边界**：某些平台构建可能需要写入缓存或签名服务，但应限制 job、环境和 secret，并保留可审计的构建 ID；不能用全局写权限解决工具配置问题。

**常见错误**：把 artifact 当缓存；把 GitHub Pages 部署权限放到测试 job；上传包含密钥的完整环境日志。

**验证方法**：审查工作流权限块，故意让测试 job 无写权限仍能完成；检查 artifact 内容没有秘密且可下载；测试失败时能拿到命令、退出码和日志。

**游戏映射**：大型二进制资产缓存、Unity Library、UE DerivedDataCache 只加速；真正的构建包、符号和测试报告必须有构建 ID 并能回滚。
</details>
