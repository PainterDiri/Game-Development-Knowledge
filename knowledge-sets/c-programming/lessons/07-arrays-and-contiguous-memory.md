# 7. 数组与连续内存：索引必须有上界

函数边界已经建立，现在要处理游戏最常见的数据形状：一批敌人、一帧输入、一段顶点、一个固定容量的房间列表。C 数组是一段连续元素，不携带运行时长度；长度必须由设计者保存并传递。

## 数组的两个事实

```c
int health[3] = {100, 50, 0};
for (size_t i = 0; i < 3; ++i) {
    printf("%d\n", health[i]);
}
```

数组元素按 `health[0]` 到 `health[2]` 连续排列；合法索引是 `[0, 3)`。`sizeof health / sizeof health[0]` 在数组仍处于数组语境时得到元素数，但数组作为函数参数时会退化为指针，因此长度不能在函数内部用 `sizeof` 恢复。

```c
void heal_all(int health[], size_t count, int amount) {
    for (size_t i = 0; i < count; ++i) health[i] += amount;
}
```

函数契约是 `pointer + length`。空数组用 `count=0` 表示，不要求传入一个可解引用的元素。

## 故意失败：`<=` 和错误容量

```c
for (size_t i = 0; i <= count; ++i) { /* 错：多访问一个 */ }
```

越界写可能改掉相邻变量、函数指针或分配器元数据，因此“这次没有崩”不是安全证据。把容量和当前长度分开：`capacity` 是分配空间，`count` 是有效元素数，始终保持 `0 <= count <= capacity`。

## 数据布局与游戏映射

连续数组有缓存局部性，适合批量更新敌人；但删除中间元素可能需要移动，指针指向元素也可能因扩容失效。高层容器会隐藏部分细节，却仍然要付出容量、迭代器失效和分配成本。Unity 的 `NativeArray`、UE 的 `TArray` 也围绕长度、容量和生命周期做工程取舍；学习 C 是为了能读懂这些契约，而非手写所有容器。
