# 14. 测试、模块设计与性能证据：把知识交付成可维护组件

前十三章分别建立了对象、边界、函数、模块、内存和错误模型。本章不再增加大量语法，而是回答工程问题：怎样证明组件在正常与失败路径都成立？怎样让性能结论来自测量而不是直觉？怎样让 API 在 Unity/UE 适配时不把领域规则和引擎对象搅在一起？

## 14.1 测试分层

- **单元测试**：固定输入验证一个函数或模块的规则；快，失败定位窄；
- **性质/不变量测试**：对实际枚举或生成的 seed、容量、序列检查约束；可发现样例遗漏，但有限测试不证明任意输入都成立；
- **集成测试**：验证多文件、文件格式、CLI 和构建入口；
- **冒烟测试**：从用户入口启动，确认最小可用路径；
- **Sanitizer 运行**：在测试路径上寻找地址和 UB 错误。

测试不应只断言输出字符串。对状态组件还应断言失败原子性、checksum、错误码和所有权后置条件。随机测试必须保存 seed 和最小失败输入。

## 14.2 API 是可验证的协议

一个好接口写清：

```text
状态拥有者：RgRuntime
输入：指针是否可空、长度、单位、范围
成功：哪些字段改变、输出参数写什么
失败：错误码、状态是否保持、日志/诊断
生命周期：借用何时失效、谁释放
线程：是否只允许单线程调用
```

`main` 只负责解析 CLI 和展示错误；规则模块不应直接打印 UI。事件通知可让上层刷新，但不能把关键顺序藏在事件回调中。数据定义（如 `EnemyDefinition`）与运行时实例（如 `EnemyInstance`）分离，避免把配置和可变状态混为一物。

## 14.3 性能需要基线

先测量再优化。记录输入规模、编译选项、机器/工具版本、重复次数、平均/分位时间和峰值内存。一个 O(n) 扫描可能比复杂数据结构更快，也可能在数十万实体时成为瓶颈；缓存局部性、分配次数和分支预测都会影响实际结果。优化后必须重跑正确性测试和基准，不能以一次快跑替代统计。

```bash
make clean && make all
make test
make asan
```

本课程运行时以固定容量数组为主，取舍是上限明确、地址稳定、无单项 free；若规模变化或稀疏删除成本成为瓶颈，再测量动态容器和交换删除方案。

## 14.4 组件实践的验收闭环

用 `code/runtime-kit/` 的 `RgRuntime` 完成：初始化 seed → 生成波次 → 查询敌人 → 命中并清除 → 输出 checksum。测试 0、恰好容量、超容量、NULL、越界、负伤害、相同 seed 和损坏输入。把循环改成 `<=` 运行 `make asan`，修复后保留回归测试。CLI 的输出不应成为唯一证据，测试需直接验证状态。

Unity/UE 适配时，C 核心只暴露稳定标量、快照或句柄；引擎层拥有 GameObject/Actor 和线程调度。ABI、编译器、结构体布局和字符串编码都属于边界，不能把内部指针直接当跨语言协议。

## 进一步拆解与实验

## 14.5 从规则到测试：先写性质，再写样例

例子测试回答“这个输入得到这个输出”，性质测试回答“所有满足前置条件的输入都不能违反规则”。以固定容量生成器为例：

```text
对任意合法 seed 和请求数量 n：
0 <= enemy_count <= capacity
每个有效敌人的 health >= 0
失败的超容量请求前后 checksum 相同
同 seed + 同命令序列得到同 checksum
```

这些是需要验证的性质声明，不是已经完成的全称证明。失败原子性的测试应逐字段比较 RNG、计数、生命、波次和敌人记录；checksum 可能碰撞，只作为快速诊断。也不能直接 `memcmp` 整个结构体，因为填充字节可能与业务状态无关。

样例仍然需要：`n=0`、`n=1`、恰好容量、超过容量、NULL、最大伤害。性质和边界互相补足；只写一个“seed=42 的黄金输出”会把实现细节误当规则，过度依赖黄金文件也会让合理重构难以进行。

## 14.6 模块边界的测试替身

规则模块不应直接依赖终端、Unity `GameObject` 或全局时钟。若需要随机数、文件或日志，可把接口作为参数或边界适配：

```text
领域函数：输入 Runtime、命令、显式 seed → 新状态/错误码
CLI 适配器：文本 → 命令；状态/错误码 → stdout/stderr
Unity 适配器：MonoBehaviour/输入事件 → 领域命令；快照 → 表现层
```

这样单元测试可以直接构造状态并断言，不必启动引擎。集成测试再验证适配器的序列化、命令行和构建入口。测试替身不是为了掩盖真实依赖；它要和真实实现共享契约，并由至少一个集成测试校验接缝。

## 14.7 性能实验的可复现记录

一次基准至少记录：提交 ID、编译器和版本、`CFLAGS`、操作系统/架构、输入规模、seed、预热次数、测量次数、平均值和分位数。改变一个变量后再比较，并先用字段级断言、独立预期输出和回归测试确认规则没有变化；checksum 只能辅助定位差异，不能证明状态相等。

```bash
/usr/bin/time -p ./arena --seed 42 < commands.txt
```

在已构建的个人主实践目录先按实践页准备 commands.txt。这里 -p 用于观察 real/user/sys 的粗粒度用时，不足以评估亚毫秒规则函数。不同系统的 `time` 选项不同，shell 关键字 time 也不一定是 /usr/bin/time；应查当前工具的帮助或手册，不假定 BSD/macOS 支持 --help。微基准需批量迭代和单调高精度时钟，并控制输入规模及输出开销。若测量结果差异小于噪声，结论应写成“不足以证明改善”，而不是挑一次最快结果。

## 14.8 课程出口的能力检查

合上答案后，学习者应能口头解释：一个输入从 CLI 进入哪个模块，哪个对象拥有状态，哪一步可能失败，失败时哪些字段不能改变，测试如何观察它，若接入 Unity 哪一层负责表现。若只能背出 `make test`，却不能解释测试覆盖的规则和遗漏的边界，说明课程还没学会。

## 本章练习

### C14-Q1：为失败路径设计测试矩阵

**题型**：测试矩阵设计
**作答产物**：输入维度×预期结果矩阵、最小覆盖集和遗漏风险。

为 `spawn_wave(runtime, count)` 列出至少六个测试维度，并说明每个要验证什么。


<details><summary>讲解、判定与验证</summary>

可覆盖 count=0、1、剩余容量恰好、超容量、runtime=NULL、不同 seed/同 seed、内部计数已满、分配/解析失败（若适用）。成功断言数量和字段范围，失败断言错误码，并逐字段比较 seed、count 及有效元素与调用前快照不变；checksum 仅作补充。用 `make test` 和 Sanitizer 执行；常见错误只测成功生成。游戏映射：波次生成失败不应半生成一组敌人。
</details>

### C14-Q2：性能改进必须同时证明正确性

**题型**：基准数据计算、实验设计与回归判定
**作答产物**：两组 median/p95 近似值、提升比例、结论与复现实验清单。

同一固定 seed、10000 个敌人的单帧规则更新，单位 ms：

```text
baseline : 10.2, 10.0, 10.4, 10.1, 10.3, 10.2, 10.1, 10.5, 10.0, 10.2
optimized:  8.1,  8.0,  8.2,  7.9,  8.1,  8.0,  8.2, 14.8,  8.0,  8.1
```

优化版的 checksum 与基线相同，但日志显示它把两个死亡敌人的顺序交换了。回答：

1. 计算两组中位数；用“排序后第 10 个值”作为本题 p95 近似，写出两组值；
2. 按中位数计算相对耗时下降百分比；
3. 是否可以合并？分别讨论规则语义允许/不允许死亡敌人重排；
4. 下一轮实验至少要记录哪些环境、正确性和资源证据。

<details><summary>讲解、判定与验证</summary>

baseline 排序为 `10.0,10.0,10.1,10.1,10.2,10.2,10.2,10.3,10.4,10.5`，中位数 `(10.2+10.2)/2=10.2`，题设 p95 近似为 10.5。optimized 排序为 `7.9,8.0,8.0,8.0,8.1,8.1,8.1,8.2,8.2,14.8`，中位数 8.1，p95 近似 14.8。中位数耗时下降约 `(10.2-8.1)/10.2≈20.6%`，但优化版出现严重长尾。

checksum 相同不是完整正确性证明，尤其可能碰撞或根本未编码顺序。若死亡敌人顺序影响回放、稳定 ID、掉落/RNG 消耗、网络快照或后续遍历，重排就是语义回归，不能合并；应修复算法或明确迁移协议。若契约明确声明死亡记录顺序无语义，所有消费者按稳定 ID 工作，并且性质/集成测试证明结果等价，则重排可接受，但 14.8 ms 长尾仍需定位并与帧预算比较。

下一轮记录：编译器/优化/目标架构、CPU 频率与电源状态、运行时和线程数、冷/热缓存、输入数据与 seed、预热/采样方法、原始样本；正确性上逐字段比较活敌人、ID 集合、事件/RNG 状态和失败路径，而非只看 checksum；资源上记录分配次数、峰值内存、cache miss/trace 与长尾堆栈。运行单元、性质、回放、Sanitizer 和目标平台基准。

评分点：数值正确；同时识别“中位数改善、尾部恶化、语义可能变化”；合并结论依赖已写明的顺序契约。常见错误是只报告最快一次，或为性能删除可观测性与边界检查。游戏映射：动作游戏优化必须满足帧预算，也必须保持确定性、命中顺序和联机状态一致。
</details>

### C14-Q3：模块测试替身应该替代什么

**题型**：模块边界与测试替身设计
**作答产物**：依赖边界图、替身接口、保留的真实规则和集成测试。

`spawn_wave` 同时读取 RNG、分配敌人数组和写日志，测试很难稳定。请指出一个合理的模块边界，并说明测试替身不能掩盖哪些真实问题。

<details><summary>讲解、判定与验证</summary>

可以让规则模块接收随机源、分配器和日志接口，测试时注入固定 RNG、失败分配器和内存日志；规则测试验证输入到输出的性质，集成测试再验证真实分配器、真实文件或平台接口。边界是替身必须保留真实接口的失败契约，不能把所有调用都变成“永远成功”；常见错误是只测 mock 交互次数而不测敌人状态，或完全没有真实集成测试。验证应包含固定 seed、分配失败、日志失败和真实实现冒烟，并比较返回值与运行时状态。游戏映射：把 RNG、资源加载和平台服务隔离，能让战斗规则可复现，同时保留对真实引擎接缝的检查。
</details>


## 课程总验收

从主仓库根目录按实践页初始化参考代码副本到 `.practice/c-programming/`，只编辑副本；运行 `make clean && make all`、`make test`、`make asan` 和固定 seed CLI。能解释每一条命令的输入、输出、状态改变、失败恢复和 Git 隔离，才算完成本课程，而不是只看到“编译成功”。
