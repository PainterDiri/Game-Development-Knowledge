# 14. 测试、模块设计与性能证据：把知识交付成可维护组件

前十三章分别建立了对象、边界、函数、模块、内存和错误模型。本章不再增加大量语法，而是回答工程问题：怎样证明组件在正常与失败路径都成立？怎样让性能结论来自测量而不是直觉？怎样让 API 在 Unity/UE 适配时不把领域规则和引擎对象搅在一起？

## 14.1 测试分层

- **单元测试**：固定输入验证一个函数或模块的规则；快，失败定位窄；
- **性质/不变量测试**：验证任意 seed、容量或序列都满足约束；发现边界更强；
- **集成测试**：验证多文件、文件格式、CLI 和构建入口；
- **冒烟测试**：从用户入口启动，确认最小可用路径；
- **Sanitizer 运行**：在测试路径上寻找地址和 UB 错误。

测试不应只断言输出字符串。对状态组件还应断言失败原子性、checksum、错误码和所有权后置条件。随机测试必须保存 seed 和最小失败输入。

## 14.2 API 是可验证的协议

一个好接口写清：

```text
状态拥有者：RgRuntime
输入：指针是否可空、长度、单位、范围
成功：哪些字段改变、输出参数写什么
失败：错误码、状态是否保持、日志/诊断
生命周期：借用何时失效、谁释放
线程：是否只允许单线程调用
```

`main` 只负责解析 CLI 和展示错误；规则模块不应直接打印 UI。事件通知可让上层刷新，但不能把关键顺序藏在事件回调中。数据定义（如 `EnemyDefinition`）与运行时实例（如 `EnemyInstance`）分离，避免把配置和可变状态混为一物。

## 14.3 性能需要基线

先测量再优化。记录输入规模、编译选项、机器/工具版本、重复次数、平均/分位时间和峰值内存。一个 O(n) 扫描可能比复杂数据结构更快，也可能在数十万实体时成为瓶颈；缓存局部性、分配次数和分支预测都会影响实际结果。优化后必须重跑正确性测试和基准，不能以一次快跑替代统计。

```bash
make clean all
make test
make asan
```

本课程运行时以固定容量数组为主，取舍是上限明确、地址稳定、无单项 free；若规模变化或稀疏删除成本成为瓶颈，再测量动态容器和交换删除方案。

## 14.4 组件实践的验收闭环

用 `code/runtime-kit/` 的 `RgRuntime` 完成：初始化 seed → 生成波次 → 查询敌人 → 命中并清除 → 输出 checksum。测试 0、恰好容量、超容量、NULL、越界、负伤害、相同 seed 和损坏输入。把循环改成 `<=` 运行 `make asan`，修复后保留回归测试。CLI 的输出不应成为唯一证据，测试需直接验证状态。

Unity/UE 适配时，C 核心只暴露稳定标量、快照或句柄；引擎层拥有 GameObject/Actor 和线程调度。ABI、编译器、结构体布局和字符串编码都属于边界，不能把内部指针直接当跨语言协议。

## 进一步拆解与实验

## 14.5 从规则到测试：先写性质，再写样例

例子测试回答“这个输入得到这个输出”，性质测试回答“所有满足前置条件的输入都不能违反规则”。以固定容量生成器为例：

```text
对任意合法 seed 和请求数量 n：
0 <= enemy_count <= capacity
每个有效敌人的 health >= 0
失败的超容量请求前后 checksum 相同
同 seed + 同命令序列得到同 checksum
```

样例仍然需要：`n=0`、`n=1`、恰好容量、超过容量、NULL、最大伤害。性质和边界互相补足；只写一个“seed=42 的黄金输出”会把实现细节误当规则，过度依赖黄金文件也会让合理重构难以进行。

## 14.6 模块边界的测试替身

规则模块不应直接依赖终端、Unity `GameObject` 或全局时钟。若需要随机数、文件或日志，可把接口作为参数或边界适配：

```text
领域函数：输入 Runtime、命令、显式 seed → 新状态/错误码
CLI 适配器：文本 → 命令；状态/错误码 → stdout/stderr
Unity 适配器：MonoBehaviour/输入事件 → 领域命令；快照 → 表现层
```

这样单元测试可以直接构造状态并断言，不必启动引擎。集成测试再验证适配器的序列化、命令行和构建入口。测试替身不是为了掩盖真实依赖；它要和真实实现共享契约，并由至少一个集成测试校验接缝。

## 14.7 性能实验的可复现记录

一次基准至少记录：提交 ID、编译器和版本、`CFLAGS`、操作系统/架构、输入规模、seed、预热次数、测量次数、平均值和分位数。改变一个变量后再比较，并先确认输出 checksum 与基线一致。

```bash
/usr/bin/time -l ./arena --seed 42 < commands.txt
```

不同系统的 `time` 选项不同，不能把示例开关当成可移植标准；先运行 `time --help` 或使用项目内统一脚本。若测量结果差异小于噪声，结论应写成“不足以证明改善”，而不是挑一次最快结果。

## 14.8 课程出口的能力检查

合上答案后，学习者应能口头解释：一个输入从 CLI 进入哪个模块，哪个对象拥有状态，哪一步可能失败，失败时哪些字段不能改变，测试如何观察它，若接入 Unity 哪一层负责表现。若只能背出 `make test`，却不能解释测试覆盖的规则和遗漏的边界，说明课程还没学会。

同时覆盖输入边界、容量、seed、状态不变和工具证据。
</details>

<details><summary>讲解与验证</summary>

可覆盖 count=0、1、剩余容量恰好、超容量、runtime=NULL、不同 seed/同 seed、内部计数已满、分配/解析失败（若适用）。成功断言数量和字段范围，失败断言错误码且 checksum/seed/count 不变。用 `make test` 和 Sanitizer 执行；常见错误只测成功生成。游戏映射：波次生成失败不应半生成一组敌人。
</details>

### C14-Q2：为什么不能只用“快了”证明优化

某优化让一次运行从 10ms 变成 8ms。还缺什么证据？

<details><summary>最小提示</summary>

先问实验是否可重复、输入是否相同、正确性是否保持。
</details>

<details><summary>讲解与验证</summary>

需要固定输入规模/seed、编译选项和环境，重复多次报告分布而非单次值；同时运行功能、边界和 Sanitizer 测试，确认 checksum/行为不变，并记录内存和分配变化。若收益只在缓存热身后出现，应区分冷/热结果。游戏映射：帧预算优化必须证明行为不变、目标平台有效且不会把诊断能力换成不可复现。
</details>

### C14-Q3：模块测试替身应该替代什么

`spawn_wave` 同时读取 RNG、分配敌人数组和写日志，测试很难稳定。请指出一个合理的模块边界，并说明测试替身不能掩盖哪些真实问题。

<details><summary>讲解与验证</summary>

可以让规则模块接收随机源、分配器和日志接口，测试时注入固定 RNG、失败分配器和内存日志；规则测试验证输入到输出的性质，集成测试再验证真实分配器、真实文件或平台接口。边界是替身必须保留真实接口的失败契约，不能把所有调用都变成“永远成功”；常见错误是只测 mock 交互次数而不测敌人状态，或完全没有真实集成测试。验证应包含固定 seed、分配失败、日志失败和真实实现冒烟，并比较返回值与运行时状态。游戏映射：把 RNG、资源加载和平台服务隔离，能让战斗规则可复现，同时保留对真实引擎接缝的检查。
</details>

从课程根目录把参考代码复制到 `.practice/c-programming/`，只编辑副本；运行 `make clean all`、`make test`、`make asan` 和固定 seed CLI。能解释每一条命令的输入、输出、状态改变、失败恢复和 Git 隔离，才算完成本课程，而不是只看到“编译成功”。
