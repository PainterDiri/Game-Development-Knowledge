# 16. 测试、不变量与基准：把底层规则变成回归证据

工具能告诉你某次运行越界，但课程出口要求“修复后不会悄悄回来”。测试不是只测几条幸运样例，而是把对象模型中的不变量写成可重复断言。

## 最小测试断言

```c
#include <assert.h>
#include <stddef.h>

static void test_empty_range(void) {
    int out_min = 7;
    int out_max = 8;
    assert(!find_min_max(NULL, 0, &out_min, &out_max));
}
```

测试应包含：正常路径、边界、失败路径和资源清理。`assert` 适合开发期不变量；若 `NDEBUG` 关闭断言，不能把用户输入校验只放在 `assert` 中。对外部输入必须保留显式错误返回。

## 不变量清单

运行时组件可以写成：

- `0 <= count <= capacity`；
- 每个有效敌人 ID 在表中唯一；
- RNG 每次消费固定数量的状态更新；
- 失败调用不改变对外可见状态；
- destroy 后句柄不可再用于规则调用。

每条都应至少有一个测试或检查点。随机系统用固定 seed 和输出序列测试；不要测试“随机看起来很随机”这种不可判定命题。

## 基准的边界

基准要固定输入规模、编译配置、重复次数和测量方法。先用 `clock` 或平台工具建立数量级，再用采样分析器定位热点。不要把一次微基准的纳秒差异直接外推到 Unity/UE 帧预算；缓存、分配器、线程和引擎调用都会改变上下文。

## 验证与游戏映射

运行 `make test`，再运行 Sanitizer 测试；把一个 bug 修复前的失败样例保留为回归测试。固定容量敌人缓冲区适合在固定帧预算下测量，动态数组则应额外测量扩容和失败。下一章将用这些测试驱动一个完整的小型组件，而不是继续堆独立语法片段。
